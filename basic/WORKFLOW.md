# AIEO Basic 工作流（初级版规范）v0.2 阶段A细则版

> **版本定位（纪要 §三）：** 日常开发协作的最小可用流程，以人为本驱动，OK 不依赖复杂调度器/状态机。战略依据：DEC-037 纪要"先实用，后完善，Basic MVP 优先"。
> **长期原则（DEC-045）：** Basic 是独立可用的初级产品，不是中级版的临时测试环境。成熟功能择优向 Standard/Advanced 提升，**禁止反向依赖**——Basic 代码不得 import 中级版运行时模块。
> **开工定档（纪要 §五）：** S1→Basic；S2→Basic 或 Standard（按风险定）；S3→Standard；S4/S5→Advanced。选型记录于任务书与交接文档，**全程不换轨**；超能力或风险升级时经用户批准换轨并登记 decision-log。
> **首期原则（DEC-045 D2）：** 文档优先、少量脚本、人工可跑。本文档承载六模块规则；配套 `templates/` 三件套与 `tasks/` 目录约定（见 tasks/README.md）。

## 模块一：任务管理（任务接收与登记）

- 入口：用户发出需求（会话消息或任务书）。
- 登记：开工即建 `tasks/<任务ID>/`（任务ID 格式 `b-YYYYMMDD-<短名>`），requirement.md 存用户原话**不加工**，task-brief.md 按模板填写。
- 任务书必备字段（DEC-045 对齐）：任务ID、需求原文、执行者理解（与原文分开便于对账）、**验收目标**（最终要实现什么）、**优先级**（普通/高）、**当前状态**（待规划/开发中/验收中/返工/**阻塞**/完成）、**当前步骤**、**最终结果**（PASS/REJECT；阻塞不是结论，只记入当前状态）。
- 版本选型三要素记入任务书：选定版本、任务等级（S1–S5）、选型理由，批准人=用户。

## 模块二：规划协商（方案讨论与拍板）

- 流程：执行者整理"需求原文 + 自己的理解 + 初步方案与实现步骤"→经派单工具发 ChatGPT→双向对话至共识→**用户拍板**→**冻结本轮方案**（steps.md 固化步骤清单）。**未拍板不得动工。**
- 单条消息 ≤1200 UTF-8 字节，不盲发；reply 原始字节 + SHA256 归档。
- 30 分钟条款（DEC-040 边界）：**仅授权"开工方案拍板"这一个环节**——用户 30 分钟未反馈可按 ChatGPT 意见执行该环节；**不构成修改用户原始需求的授权，也不覆盖 main 合并/生产发布/数据删除等高危操作**（DEC-010 保留）。方案与用户原始需求冲突时，必须重新提交用户确认。
- **两道关口（DEC-045）：** 文档复审 ≠ 用户拍板；代码规划 ≠ 开发授权。开工前需求原文必须经用户确认。

## 模块三：开发执行

- 按拍板步骤逐条实现；每步完成后**停止并交独立验收，不得自我宣布通过**。
- `tasks/<任务ID>/steps.md` 每步记录**六要素**：①本步骤目标 ②修改文件 ③修改内容 ④执行结果 ⑤测试结果（未测项如实标注"未测"）⑥验收证据引用（dispatch 目录+reply SHA）。
- 首期人工操作 Git 与运行测试（D2）；禁止自动合并分支、禁止无人确认的 push。
- 高危红线（DEC-010）：main 合并、生产发布、数据删除必须用户拍板。
- 秘密不进 Git（C6）：敏感信息、Cookie、Token、API Key 不入库不入历史。

## 模块四：独立验收

- 每步完成 → 验收请求（`templates/acceptance-request.md`）派单 ChatGPT 独立验收。
- 结论两态（DEC-045）：**PASS**（本步通过，允许进入下一步）/ **REJECT**（退回开发修复）。特殊阻断状态 **BLOCKED**：不属于通过或失败结论，**不得进入下一步**；因环境等原因无法验收时如实标 BLOCKED 并说明，解除后恢复验收，登记于 steps.md 当前状态=阻塞。
- **验收六查（验收方自查，不得只读完工总结了事）：** ①是否符合本步骤目标 ②是否符合用户拍板方案 ③修改是否超出范围 ④有无明显代码质量问题 ⑤测试是否真实执行 ⑥证据是否可核查。
- **验收方须自行获取并核查：** 用户拍板的方案、本步骤验收标准、开发前基线 commit、实际代码修改 diff、测试执行结果及证据。
- 证据归档：派单日志（request.txt / reply.txt 原始字节 + SHA256）入 `phase0/logs/dispatch-<时间戳>/`。

## 模块五：返工管理

- REJECT → 修复 → 同一验收通道重新验收。
- **"同一问题"识别与计数规则（复审补充，两个文件统一采用）：**
  - 同一根因、同一缺陷即同一问题，**即使修复方案不同也累计计数**；
  - 一次 REJECT 含多个相互独立问题时，**分别建立问题记录**，各自计数；
  - 已解决的问题不再累计；同一根因**复发**时恢复原问题记录继续计数；
  - 第 3 次仍未通过 → **停止该问题的返工循环**，开会交用户。
- **三轮止损流程**：
  - 第 1 次 REJECT：开发方修复；
  - 第 2 次 REJECT：分析失败原因，调整修复方案后再修；
  - 第 3 次仍 REJECT：**停止循环，开会**，向用户说明失败原因/已试方案/剩余风险/可选决策，用户拍板最终做法（必须是执行者可实现且各方认可的方式）；**不得以增加参会 AI / 会话延长讨论**（AI-DEV-LESSONS §2）。

## 模块六：交付管理

- **完工六查（全部满足才交付）：** ①所有步骤均 PASS ②整体测试已完成 ③无遗留未处理 REJECT ④Git 工作区状态符合预期 ⑤已 commit ⑥完工总结已形成。
- 完工总结**七要素**（落 `tasks/<任务ID>/delivery.md`）：原始需求 / 最终实现内容 / 修改文件 / 测试结果 / Git commit / 未解决问题 / 后续建议。
- 交接文档使用唯一权威模板 `docs/phase1/handoff-template.md`（v0.3，含"任务版本选型"必填字段）。

## 会话管理（执行者自管纪律，DEC-048）

- 完整纪律见 `docs/AI-DEV-LESSONS.md` **L-015**（GLOBAL 级）：**压缩事件＝唯一可靠信号**（执行者无法直读百分比，禁止猜测/虚构）；L1 一次压缩→继续当前小任务至下一自然暂停点交接，L2 二次压缩→立即交接；**阶段完成点、大型新阶段开工前、会话将结束而任务未完成时必评估交接**，不硬撑到上下文上限。
- 交接完成＝四项齐备：①交接包（模板 v0.3，八项最小必填）②经验入档（交接包≠经验文档）③**提交并成功推送 GitHub** ④通知用户附一句话开工指令。
- 双重事实来源：Git 仓库＝代码状态事实，交接包＝意图与状态事实；新会话第一动作＝核对仓库实际状态，不一致以仓库为准并停止开发查明差异。
- 效率保护：L1 不中断当前任务；会话管理由执行者主动决策，用户无需监控。

## 代码抽取纪律（从中级版复制功能，DEC-044/DEC-045）

- **允许：** 选择性复制成熟小功能——任务数据结构思路（app/platform/tasks.py）、状态转换规则（state_machine.py）、证据校验思想（SHA-256 校验/回读验证/不稳定数据拒收）、Git 工作区与 diff 处理方式（M4 worker）。
- **禁止：** import 中级版运行时模块；整体搬迁 M1 完整平台 / M2 完整派单 / M3 / M4 完整 Worker / phase1 scheduler.py（"抽取能力，不抽取整套架构"）。
- 每份复制件登记四项：来源文件路径、源 commit 完整 SHA、修改点、对应测试（登记于任务 steps.md 或代码头注释）。
- 公共工具（派单/体检/推送）一律**引用不复制**：`phase0/tools/` 与 `toolkit/` 为唯一权威源码。

## Basic 首期不做清单（DEC-045）

多 AI 自动调度 / 自动任务领取派发 / 数据库与服务端 / 复杂契约引擎 / 自动合并分支 / 无人确认的 Git push / 复杂项目并行开发——属 Standard/Advanced 方向。

## 首个真实闭环验证任务（DEC-045 D4）

- **任务包完整性检查工具**：Python 标准库实现；输入一个 Basic 任务目录，检查任务记录完整性——基本信息是否齐全、有无用户拍板的实施方案、每个实施步骤有无独立验收记录、REJECT 有无对应返工记录、同一问题是否超过三轮、整体测试与完工总结是否存在；输出 PASS/FAIL 与具体缺失项。
- 该任务作为**阶段 C** 的验证对象，完整走四步流程（需求确认→拍板→逐步开发+独立验收→整体测试+交付）。

## 部署边界（D1 独立性的准确含义）

- Basic **不依赖 Standard 业务运行时**（不 import 中级版模块、不部署其数据库/调度器/服务端）。
- 但派单/推送等**公共工具仍在 AIEO 仓库内**（phase0/tools、toolkit）——复制到新电脑时需**保留仓库公共工具并完成环境初始化**（node、playwright、Chrome profile），不是只复制 basic/ 目录即可完整运行。

## 派单工具链（引用不复制，共识选项 A）

- **唯一权威源码：`phase0/tools/gpt_dispatch.mjs`**（含 inbound_dom.mjs 采集器）。本目录只引用，不复制脚本。
- 依赖：node ≥18、playwright（`phase0/tools/node_modules`）、Chrome gpt-poc profile（`runtime/chrome_profiles/gpt-poc`，CDP 9222）、会话锁 `phase0/e2e-poc/session_lock.mjs`。
- 纪律：单条 ≤1200 字节；reply 原始字节 + SHA256 归档；会话 URL 不得写入 shell 命令行（派单守卫拒绝）；Chrome 启停走冻结工具内建流程，临时脚本不得接管浏览器生命周期。验收结论必须绑定：对应步骤 + 待验收 commit 完整 SHA + 证据目录。
- 环境预检：`node toolkit/check-env.mjs`；推送诊断与执行：`node toolkit/check-push.mjs`（推送活端口动态获取，注册表 ProxyServer，勿写死——见 phase0/environment-inventory.md）。
