# 需求登记：动态任务调度（并行上限 3 + 协商式抢占）

**登记时间：** 2026-11-23
**需求来源：** 用户指令（2026-11-23 两轮确认）
**状态：** 需求已明确，方案待 ChatGPT 复审；未获实施授权（DEC-010 红线不变）

## 1. 用户原话

1. "临时加任务（总任务不超过3个）是否能实现，假设开始三个任务，做完一个，打断再加一个任务；或者开始两个任务开发中，中间再加一个，这样可以随时安排任务"
2. "3是目前的并行上限，不是待办队列长度上限，超过3的要等待；允许中断正在跑的任务，要与我协商，比如任务A临时加急处理，如果加上任务A之后，并行的数量超过3，则正在跑的任务B需要让路，B要暂停或者直接终止先交接出来"

## 2. 规则澄清（用户已拍板）

| 规则 | 定义 |
|---|---|
| 并行上限 = 3 | 指**同时在执行（RUNNING/DISPATCHED）的任务数上限**，不是待办队列长度。第 4 个及以后进入 WAITING 等待，不拒绝创建 |
| 动态加任务 | 任何时刻可创建新任务；创建后按是否超并发上限决定立即调度或进入等待队列 |
| 抢占 = 协商式（人在回路） | **不允许 AI 自动抢占**。加急任务加入导致并发将超 3 时，系统生成"让路协商请求"提交用户，由用户拍板：①哪个在跑任务让路；②该任务"暂停交接"（SUSPENDED）还是"终止交接"（CANCELLED）。未获用户决策前，不执行抢占 |
| 让路任务交接 | 被让路任务须先完成当前派单轮采集/补采（禁重发语义不变），再落盘交接包（进度/证据/未完成项/恢复条件），然后变更状态并释放并发名额给加急任务 |
| 恢复 | SUSPENDED 任务仅在用户明确指令下恢复（与已有 v1.0 设计"SUSPENDED→RUNNING 仅人工确认解除"一致）；CANCELLED 终态，产物保留 |

## 3. 典型场景

- 场景 A：3 个任务在跑 → 完成 1 个（释放名额）→ 加 1 个 → 新任务直接调度，无抢占。
- 场景 B：2 个在跑 → 中间加 1 个（达到 3）→ 正常调度，无抢占。
- 场景 C：3 个在跑 → 加急任务 A 要插入 → 并发将达 4 → 触发协商：列出 3 个在跑任务供用户选让路者 + 暂停/终止选项 → 用户拍板 → 被让路任务交接释放名额 → A 进入执行。

## 4. 边界（继承已有治理，不因新需求放松）

- 派单通道全局串行不动（session_lock v6），"派单串行≠开发串行"仍成立；并发上限 3 管的是"在执行的开发任务数"，不是并发派单数。
- 一任务一会话一 worktree 一分支（M2 治理 v0.1 生效）；每会话同一时刻仅绑一任务。
- M4 写操作封闭、DEC-010（main 合并/生产发布/数据删除）红线、证据五件套、906⑥ 平台级并发门——均不被本需求自动解除。
- 新状态机/并发计数器/协商接口须经独立审查 PASS 后方可实施；本需求登记不构成实施授权。
