一、四个讨论点的裁定
1. 清单放 prompt 还是 params？

推荐：双写，但职责不同。

位置

	

职责

	

是否必需




prompt 文本

	

让图像模型理解每个产品的视觉约束

	

必需




params 结构化字段

	

供后端校验、审计、调试及未来供应商适配

	

必需

原因：

供应商现有接口已经接受 prompt，不需要供应商改造。

结构化字段不会因为提示词格式变化而丢失。

prompt 是模型实际理解的内容，params 是系统可验证的事实，两者不能互相替代。

建议结构：

JSON
{
  "prompt": "原有设计提示词 + 产品占比清单",
  "external_ref": [],
  "params": {
    "product_constraints": [
      {
        "name": "产品名称",
        "color_variant": "颜色/规格",
        "score": 0.92,
        "screen_coverage": 0.18
      }
    ]
  }
}

注意：这里是请求层的目标结构示意，不代表现有供应商 params 已支持该字段。

重要约束：

screen_coverage 必须沿用选品冻结结果的原始语义和单位。

不得将缺失值伪造为 0。

不得重新计算 score 或占比。

清单必须与本次实际选中的产品一一对应。

2. 清单是否进入 compose_prompt？

推荐：进入 compose_prompt，合并进 resolved_prompt 冻结。

不推荐 worker 临时拼接另一段提示词。

理由：

resolved_prompt 应当代表本次 Job 实际执行的完整提示词。

任务重试必须复用相同提示词。

调试时可以直接追溯模型实际收到的设计约束。

避免 compose_prompt 与 worker 各自维护一套产品约束表达。

建议提示词增加独立区块：

纯文本
【产品选择与画面占比约束】

以下产品均为本次设计必须参考的产品。
请使用对应产品原图作为外观、颜色和材质依据。

1. 产品：XXX
   颜色规格：XXX
   评分：0.92
   画面占比：18%

2. 产品：YYY
   颜色规格：YYY
   评分：0.88
   画面占比：15%

共计6项。
请保持产品外观与参考原图一致，并尽可能遵循上述画面占比。

这里有一个特别重要的语义问题：

评分是选品依据，不一定是图像生成约束。

建议：

名称、颜色、占比：作为生成约束。

score：作为选品审计信息，不要求模型按照分数改变视觉效果。

评分不得被解释为产品优先级或画面占比。

另外，占比属于生成模型的软约束，不能承诺最终像素级占比精确达标。

3. ReferenceSelection 冻结契约是否保持不动？
保持不动

这是本次方案最重要的架构边界。

不修改：

Job.reference_selection_json

selected 的现有字段定义

rank / score / screen_coverage 的计算规则

resolved_assets 的解析规则

variant → default → product_image 原图回退顺序

原图去重和发送逻辑

只扩展：

compose_prompt：读取冻结选品结果，生成产品约束文本。

worker 请求组装层：生成结构化 product_constraints。

必要的请求模型及校验逻辑。

3. Golden parity

这里建议明确区分两个概念：

旧 golden：原有提示词行为，防止无关内容被修改。

新 golden：包含产品约束区块的完整 resolved_prompt。

不能简单要求新旧 prompt 字符串完全一致，因为本次需求本来就需要增加内容。

应验证：

原设计提示词主体没有非预期变化。

产品清单内容与冻结数据一致。

数字格式和单位稳定。

同一输入重复生成得到相同结果。

产品排列顺序稳定。

不出现重复产品约束区块。

四、最终推荐实施路径

建议按以下顺序实施，避免一次修改过多层次。

第一步：定义请求层数据契约

明确 product_constraints 字段、类型、单位、缺失值规则及排列顺序。不改 ReferenceSelection。

第二步：扩展 compose_prompt

从冻结的 selected 数据生成产品约束区块，写入 resolved_prompt。

第三步：扩展 worker 请求组装

从相同冻结数据生成 params.product_constraints；保持 external_ref 原有行为。

第四步：补齐测试

TS → pytest → golden parity → worker 集成测试。

第五步：验收请求快照

检查实际发出的 prompt、params、external_ref，证明三者来自同一份冻结选品数据。
