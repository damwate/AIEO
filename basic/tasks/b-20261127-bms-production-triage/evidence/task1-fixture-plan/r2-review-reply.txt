二、必须整改的两个问题
P1-1：SQL LIKE 前缀匹配没有转义下划线

这是本轮最重要的问题。

方案使用：

SQL
WHERE user_name LIKE 'acl_it_fixture_%'

以及：

SQL
WHERE qywx_user_id LIKE 'acl_it_fixture_%'

但是 MySQL 的 LIKE 中：

_ 代表任意单个字符。

% 代表任意长度字符串。

因此，acl_it_fixture_% 并不是严格意义上的 acl_it_fixture_ 前缀。

它可能匹配到其他并不属于 fixture 命名空间的数据。

尤其需要注意：这个查询不仅用于检查，还用于识别遗留用户并执行逻辑删除。

要求：

改成具有明确字面前缀语义的查询，例如：

SQL
WHERE LEFT(user_name, CHAR_LENGTH(%s)) = %s

参数均使用预编译绑定，前缀固定为 acl_it_fixture_。

qywx_user_id 同样处理。

这样可以避免通配符误匹配，确保清理范围严格限定在专用命名空间。

P1-2：多个测试进程同时运行时可能互相清理

当前设计是：

每次运行生成新 runid。

@BeforeClass 检查整个 fixture 前缀。

发现活跃残留就执行逻辑删除。

创建本轮 fixture。

这在单进程顺序执行时没有明显问题。

但如果两个测试进程同时启动：

进程 A 创建了自己的 fixture。

进程 B 执行前缀预检。

B 可能把 A 正在使用的 fixture 当作异常残留删除。

这会导致测试出现随机失败。

要求：

增加跨进程互斥机制。

推荐使用数据库命名锁（例如 MySQL GET_LOCK），但需要特别注意：

锁必须覆盖残留检查、fixture 创建、整个测试生命周期及清理。

持锁连接必须保持有效。

异常和进程退出时必须考虑锁释放。

获取锁失败时必须 fail-closed，不能继续执行。

不能把锁机制改造成生产业务逻辑。

如果不想增加数据库锁，也可以明确限制该测试运行器同一时刻只能有一个实例，但必须有可靠的进程级互斥保证，不能只写文档声明。

三、补充整改要求

这两项不单独升级为 P1，但应在方案修订时明确。

1. 清理顺序固定

建议明确为：

@After：每个测试结束，吊销该测试登记的 token。

@AfterClass：先按 fixture userId 查询并吊销剩余活跃 token。

再对 fixture 用户执行 userService.deleteById。

最后释放跨进程互斥锁。

不能先删除用户，再依赖用户关联查询清理 token。

2. 清理必须验证结果

不能只调用删除方法就认定成功。

清理后应检查：

fixture 用户 is_deleted=1。

fixture 用户关联 token 全部 is_deleted=1。

fixture 命名空间没有非预期活跃记录。

不出现物理 DELETE。

如果清理失败，必须使本轮验收失败，并输出残留记录的审计信息。
