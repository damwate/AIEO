Q2：最小闭环排序，P0 与缓存合流并行还是串行？
修改后同意

我的裁定：串行确定正确性基线，随后并行推进缓存与格式治理。

不建议让缓存合流成为截图正确性的前置条件。

原因是：

缓存解决重复下载和冷启动性能问题；capture gate 解决截图正确性问题。

即使缓存完全命中，仍然可能遇到：

纹理解码延迟。

资源加载失败。

GPU 上传延迟。

材质绑定异常。

因此不能用缓存命中替代加载完成判定。

建议顺序：

第一阶段：正确性闭环（最高优先级）

capture gate 纳入 CacheEntry.loaded。

采用 settled 语义，区分成功与失败。

Billboard 未加载不显示。

photo 路径补充截图门禁。

超时或必要资源失败时拒绝生成成功截图。

第二阶段：并行治理

两条工作流可以并行：

A. 缓存合流：消除每次开页重复下载 80MB 的冷载问题。

B. 格式准入：415 拒绝、Catalog 校验、Worker 出口校验。

第三阶段：端到端防复发

GDC 传递资源就绪证据。

AISVC record-only 检测输入图片。

记录白块检测结果与资源加载状态。

用真实冷启动、热启动场景复验。

这里有一个关键技术细节：

CacheEntry.loaded 不应该直接作为所有资源的唯一终态。

Q3：render_assets_ready 放 GDC 提交表单还是 AISVC params_json？
修改后同意

建议：放在 GDC → AISVC 的任务提交参数中，进入 params_json，但不放在用户可编辑的表单字段中。

理由：

render_assets_ready 是系统运行状态，不是用户业务输入。

GDC 最清楚 3D 场景资源加载状态。

AISVC 需要知道输入图片是否来自完整渲染，便于关联检测结果。

如果放入用户表单，用户可能修改、遗漏或伪造该字段。

建议将其定义为系统生成的只读元数据。

不过我建议对命名和语义稍作修改。

render_assets_ready 是一个布尔值，表达能力不足。

例如：

所有资源成功加载。

部分非关键资源失败。

必要纹理加载超时。

没有纹理的纯色场景。

这些情况不能简单用 true/false 混为一谈。

建议采用：

JSON
{
  "render_assets": {
    "status": "ready",
    "revision": "revision-id",
    "required_total": 24,
    "loaded": 24,
    "failed": 0,
    "timeout": 0,
    "captured_at": "timestamp",
    "evidence_version": 1
  }
}

这里是建议的数据结构，不是要求现在改码。

另外有两条边界：

AISVC 不应该盲目信任这个字段，它只是 GDC 提供的上游证据。

AISVC 的 record-only 检测应独立记录检测结果，不能因为 status=ready 就跳过图像检测。

尤其是用户上传的参考图，不应该依赖 render_assets 元数据，因为它们不是 GDC 渲染产物。
