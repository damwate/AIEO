二、逐条复审意见
1. basic/WORKFLOW.md
基本通过

1.1 六模块覆盖：通过

六个模块均已形成可执行的基本流程：

任务管理：需求原文、任务书、版本选型。

规划协商：双向讨论、用户拍板、步骤冻结。

开发执行：逐步实施、逐步验收。

独立验收：六查、证据核验。

返工管理：同一问题三轮止损。

交付管理：完工六查、七要素总结。

符合 DEC-045 的主体设计。

1.2 三轮止损：需要补充定义。

目前写了同一问题计数，不同问题分别计数，但没有定义如何判定同一问题。

建议明确：

同一根因、同一缺陷，即使修改方案不同，也累计计数。

一个 REJECT 包含多个相互独立的问题，分别建立问题记录。

已解决的问题不再累计；后续出现同一根因的复发，应恢复原问题记录。

第三次仍未通过，必须停止该问题的自动返工循环。

否则不同执行者可能对计数产生不同理解。

1.3 两道关口：需要消除授权边界歧义。

目前同时存在：

开工前需求原文必须经用户确认。

30 分钟未反馈可以按 ChatGPT 意见执行。

建议明确：

30 分钟条款只授权开工方案拍板，不代表修改用户原始需求的授权，也不覆盖 main 合并、生产发布、数据删除。

用户原始需求与方案发生冲突时，必须重新提交用户确认。

1.4 独立验收：需要补充候选 commit 约束。

目前要求验收方自行获取：

用户拍板方案。

验收标准。

开发前基线 commit。

实际代码 diff。

测试结果及证据。

但没有明确要求开发者提供本次待验收代码的 commit SHA。

建议增加：

待验收 commit SHA（完整 40 位）。

待验收分支。

测试对应的 commit SHA。

验收时实际 diff 的基线与目标 commit。

这是重要缺口。否则验收方可能读到不同版本的代码，造成验收结论无法准确绑定代码。

1.5 D4 首个验证任务：缺少明确落位。

DEC-045 明确指定首个真实闭环验证任务：

Python 标准库实现的任务包完整性检查工具，检查任务目录记录完整性，输出 PASS/FAIL 和缺失项。

当前 WORKFLOW 没有保留这一明确的首期验证任务。

建议在首期不做清单之后增加一条：

首个真实闭环验证任务为任务包完整性检查工具，作为阶段 C 的验证对象。

1.6 派单工具链：需要说明独立部署边界。

目前 Basic 依赖：

phase0/tools/gpt_dispatch.mjs

phase0/e2e-poc/session_lock.mjs

runtime/chrome_profiles/gpt-poc

Node、Playwright、Chrome 等环境。

这与 Basic 独立于 Standard 运行时的原则并非必然冲突，因为 DEC-045 已批准公共工具引用不复制。

但应明确：

Basic 不依赖 Standard 业务运行时，但当前派单工具仍依赖 AIEO 仓库中的公共工具及其环境。

复制到新电脑时需要保留仓库公共工具并完成环境初始化，不能理解为单独复制 basic/ 目录就能完整运行。

3. basic/templates/acceptance-request.md
需要修正

这是四份文件中最需要认真补充的一份。

3.1 验收标准缺少独立字段。

目前只有：

本步骤目标（拍板原文照录）

但目标和验收标准不是一回事。

例如：

目标：实现任务目录完整性检查。

验收标准：缺少 requirement.md 时必须 FAIL，并明确列出缺失文件。

建议增加：

本步骤验收标准（明确可验证的通过条件）：

否则验收方需要自行推断标准，容易造成争议。

3.2 缺少待验收 commit SHA。

建议增加：

开发前基线 commit。

本次待验收 commit。

分支名称。

测试所绑定的 commit。

这与 DEC-010 的审查绑定明确 commit 的原则一致。

3.3 自测证据应增加证据位置。

目前有命令和输出摘要，但建议明确记录：

实际执行命令。

执行结果。

原始测试日志路径。

未测项目及原因。

对应 commit SHA。

不能仅凭开发者提供的测试摘要认定测试真实执行。

3.4 两态结论的表述：建议规范化。

当前写法是：

「结论两态 PASS / REJECT；环境原因无法验收时 BLOCKED。」

逻辑可以成立，但标题容易让人误解为有三个同级结论。

建议改成：

正常验收结论：PASS / REJECT。

特殊阻断状态：BLOCKED，不属于通过或失败结论，不得进入下一步。

这既保留 DEC-045 的两态结论共识，也不丢失环境阻断处理能力。

3.5 三轮止损：通过。

已经写入同一问题计数原则，建议与 WORKFLOW 统一采用同一套问题识别规则，不要在两个文件中形成不同定义。
