一、P0：必须修复
P0-1：COMMIT 报错没有实现规定的错误码

session-budget.mjs 的写事务代码把 SQL 语句异常和 COMMIT 异常放在同一个 catch 中。

当前逻辑确实做到了：

读取 conn.isTransaction 属性；

仅在事务仍活动时尝试 ROLLBACK；

无论事务状态如何都关闭连接；

不复用该连接。

但异常最终执行的是 throw e，没有将 COMMIT 失败转换为设计要求的：

LEDGER_COMMIT_UNCERTAIN

这意味着 COMMIT 失败时，调用方拿不到约定的 UNCERTAIN 错误语义。不能把“连接已关闭”视为“COMMIT 失败协议已完成”。

整改要求： 区分 COMMIT 阶段与普通 SQL 阶段。COMMIT 报错必须关闭连接并上抛 LEDGER_COMMIT_UNCERTAIN；不得计成功、不得重放本轮。普通 SQL 错误保留各自错误语义。

P0-2：busy_timeout 设置失败被静默吞掉，绝对 deadline 存在失效路径

当前实现：

JavaScript
try { conn.exec(`PRAGMA busy_timeout=${busyMs}`); } catch {}

这里的 catch {} 会吞掉动态 busy_timeout 设置失败。

一旦设置失败，连接可能继续使用默认等待参数。随后 BEGIN IMMEDIATE 仍可能阻塞超过剩余 deadline。当前的 3000ms 保护依赖动态参数成功设置，因此不能把设置失败当作无害异常忽略。

整改要求： 动态 PRAGMA busy_timeout 设置失败必须进入 fail-closed 路径，关闭连接并抛出明确错误；不能继续执行可能超时的写事务。

P1-2：C1、C8 的“双进程并发”实际是顺序执行

测试中使用：

JavaScript
const p1 = spawnSync(process.execPath, [worker]);

spawnSync 会等待第一个进程结束，才会执行第二个进程。

因此：

C1 没有验证双进程并发更新；

P1-3：AIEO 两时点记账导致 turns 和 maxTurnBytes 失真

AIEO phase0/tools/gpt_dispatch.mjs 中：

SEND_CONFIRMED 调用一次 recordTurn(inBytes, 0)；

COMPLETED 再调用一次 recordTurn(0, outBytes)。

而核心 recordTurn() 每次调用都会：

turns + 1；

更新 maxTurnBytes。

所以一条实际对话轮次会被记成两轮；maxTurnBytes 也分别记录输入和输出峰值，而不是该轮 inBytes + outBytes 的合计峰值。

总字节数仍然可以正确累计，但轮数与单轮峰值统计不正确。这会使账本的字段语义与设计中的“轮次”不一致。

整改要求： 保留发送确认时先记输入、完成时再记输出的两时点特性，同时增加同一逻辑 turn 的关联机制，使第二次记账更新该轮，而不是再创建一轮。必须补测单轮输入输出分别记账后 turns=1 且 maxTurnBytes=inBytes+outBytes。

P1-4：新会话 UUID 延迟确认时漏记输入

gpt_dispatch.mjs 的 confirmSend() 有一条分支：

首次确认时 confirmedSessionId 为空；

这条延迟获取 UUID 的分支没有执行 recordTurn(...inBytes...)。
