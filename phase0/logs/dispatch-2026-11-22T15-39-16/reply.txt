Q2. 修改 sing-box config.json 的 process_name 是否无效？
对当前架构无效

这是本次问题最重要的技术判断。

你的当前架构：

SakuraCat / sing-box

0.0.0.0:1080 mixed inbound

SOCKS5 / HTTP 客户端请求

sing-box outbound

VPN 远端出口

问题在于：

process_name 不是一个可以从 SOCKS5 请求内容中直接读取的字段。

SOCKS5 客户端向服务器发送的是目标地址、端口和代理协商数据，并不会在协议中携带原始 Windows 客户端的 exe 名称。

因此：

sing-box 收到 wow.exe 的 SOCKS5 请求时，不能仅凭这个请求可靠地知道发起者是 wow.exe。

Windows 上 sing-box 支持 process_name，不意味着所有 inbound 都能识别原始发起进程。

process_name 更适合 sing-box 能够直接关联到原始进程的流量接管场景，例如适当的 TUN 路由。

官方文档确实列出了 Windows 的 process_name 支持，但这不意味着 SOCKS inbound 自动获得客户端进程身份。

裁定：不建议修改 SakuraCat 的 config.json 来解决这个问题。 保持现有配置不动，可以减少无关变量。

还有一个很重要的安全设置：不要使用全局代理规则，只添加 wow.exe 的精确规则。

为什么不直接推荐 Python？

Python 可以做 SOCKS5 转发，但有一个技术障碍：

普通 Python 程序只能监听、接收和转发已经交给它的连接，不能自动识别 Windows 上哪个原始进程正在发起 TCP 连接。

要实现完整功能，还需要：

Windows 网络过滤驱动，例如 WinDivert。

进程 PID 与网络连接的关联。

TCP 连接状态及数据转发。

SOCKS5 CONNECT 协议实现。

UDP ASSOCIATE（如果游戏需要 UDP）。

DNS 处理。

连接关闭、超时和异常恢复。

所以 Python 可以作为代理转发服务的开发语言，但不能靠简单写一个 Python SOCKS5 客户端，就实现按 exe 透明分流。

另外有一个开源项目值得知道：Force-Proxy。它通过 Winsock API Hook 和 DLL 注入实现 SOCKS5 转发。其 TCP/UDP 功能值得研究，但我不建议把 DLL 注入作为这次的首选，尤其是游戏程序可能存在反作弊、完整性检查或更新兼容问题。

第六步：额外检查 DNS 和 UDP

游戏代理与浏览器代理有一个区别：即使 TCP 出口正确，也不代表 DNS、UDP 全部没有泄漏。

建议：

ProxyBridge 先设置 Both，而不是仅 TCP。

检查游戏是否有 UDP 连接。

检查 DNS 查询是否由游戏进程发出，还是由 Windows DNS Client（通常是 svchost.exe）代为发出。

使用 DNS 泄漏检测网站进行辅助检查。

如果 DNS 仍然直连，需要单独设计 DNS 转发策略，不能简单把 svchost.exe 全部代理，否则会影响其他程序。

另外，游戏可能存在独立启动器、更新器和登录进程。需要根据连接日志决定是否增加规则，不能直接扩大匹配范围。

第七步：回滚方案

如果出现游戏无法连接、延迟异常或其他程序受到影响：

先关闭 ProxyBridge 规则或停止过滤。

检查其他程序是否恢复直连。

退出 ProxyBridge。

检查 SakuraCat 仍然保持原有状态。

如果需要彻底卸载，再通过正常卸载流程清除 ProxyBridge 及其驱动。

ProxyBridge 使用的是网络过滤驱动，不是 TUN，但它确实有内核级网络拦截能力。因此，建议先小范围测试，不要直接设置开机自动运行。
