二、两个必须整改的 P1
P1-1：进程归属查询失败时，代码会放行端口复用

位置：phase0/tools/gpt_dispatch.mjs 的 countChromeProcessesForProfile 和 startChromeWithDebugPort。

当前逻辑：

PowerShell 查询 Chrome 进程。

如果解析到 count=N，返回数量。

如果 PowerShell 执行失败，或者输出无法解析，返回 null。

调用方只判断 ownProcs === 0。

null 不等于 0，于是继续执行端口复用。

也就是说：

当前危险分支

CDP 端口可访问

进程归属查询失败，返回 null

null === 0 为 false

错误放行：复用未经证明归属的 CDP 端口

这直接违反 DEC-123 的“归属不明不复用、fail-closed”要求。

整改要求：

PowerShell 执行错误必须视为归属核验失败。

输出格式无法解析必须视为归属核验失败。

只有明确核验到本实例进程，才能复用。

明确查到 0 个本实例进程时，按 foreign 处理。

null、异常、超时等未知状态统一停止，不得继续连接。

这项是实质性安全边界，不接受仅补测试断言而不修正调用逻辑。

P1-2：端口注册表只检查外层结构，没有检查映射完整性

位置：gpt_dispatch.mjs 的 readPortRegistry，以及 dispatch_options.mjs 的 allocateInstancePort。

目前注册表只验证：

version === 1

ports 是非空值的对象

没有验证每一条映射：

instance ID 是否符合规范；

port 是否为有效整数；

port 是否位于允许的候选范围；

不同实例是否登记了相同端口；

是否存在 default 端口被命名实例占用等非法映射。

更关键的是，allocateInstancePort 对已登记实例直接返回原端口，不会重新验证注册表中的映射是否满足唯一性约束。

正常程序写入时有注册表锁，确实能防止正常并发分配竞态；但锁不能证明已有注册表内容一定合法。

整改要求：

注册表读取时逐项验证 ID、端口类型、范围和唯一性。

任一映射不合法或重复，返回 INSTANCE_REGISTRY_INVALID，不得继续。

已登记端口复用时仍须完成归属核验。

不得因为注册表已有记录，就跳过端口碰撞和进程归属安全检查。

三、recoll 同锁约束：尚未闭合

DEC-123 的实例域设计明确要求：

派单与 recoll 必须使用同一实例 ID、同一锁路径。

但当前 review_leg_recoll_driver.mjs 仍然是：

固定 CDP 127.0.0.1:9222；

未从 --instance 派生实例锁和浏览器端口。

交付记录已经如实披露了这件事，我认可它没有把未完成内容冒充 PASS。

不过，必须区分两个概念：

当前 recoll 只运行在 default 域：可以作为阶段1本地测试的限制。

未来命名实例运行 recoll 时也能取得对应实例锁：目前没有实现证据。

因此这一项目前是 BLOCKED。阶段2申请之前，必须明确是否纳入整改；不能在真实并发试跑时让命名实例 dispatch 与 default recoll 各自拿不同锁，却共同操作同一浏览器资源。
