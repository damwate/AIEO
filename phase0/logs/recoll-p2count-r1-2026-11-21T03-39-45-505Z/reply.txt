你的成本考虑成立：如果每增加一个实例都必须人工重新登录，实例扩容会产生不必要的运维成本。

1. Profile 克隆规程

建立黄金源 profile

使用现有已经登录的 default profile 作为模板。确认账号身份、登录有效、没有安全验证页面。

彻底关闭 Chrome

关闭所有使用该 user-data-dir 的 Chrome 进程。不能只关闭窗口而让后台进程继续运行。

完整复制

将完整 user-data-dir 复制到独立目录，而不是只复制 Default 子目录。

例如：

profiles/gpt-poc-agent-a

profiles/gpt-poc-agent-b

profiles/gpt-poc-agent-c

必须包含正确的 Local State 和 Profile 数据。

实例隔离

每个实例使用自己的 user-data-dir、DEBUG_PORT、INSTANCE_ID 和锁。

禁止两个 Chrome 进程同时使用同一份 profile。

逐实例登录态验收

先逐个启动实例，检查 ChatGPT 页面是否已登录、账号身份是否正确、是否出现安全验证或限流页面。

不读取或导出 Cookie，不将凭据写入日志。

验证通过才开放派单

每个实例必须有独立的登录状态检查结果。全部完成后才允许进入 N=2 并发试跑。

二、生产实例数：建议先定 N=3，不直接定死 N=4

这里必须区分三个不同问题。

1. 技术承载能力

你的判断基本正确。

Chrome 每个实例都有独立进程、profile、端口和锁，实例数量增加会增加：

Chrome 内存占用；

CPU 和页面渲染开销；

CDP 连接数量；

进程清理与故障恢复复杂度。

但这不是目前最主要的扩容瓶颈。

2. 账号实际承载能力
真正的扩容限制

同一个 ChatGPT 账号的多个浏览器实例，不会因此获得多份独立账号配额。

并发增加意味着：

多个实例同时消耗同一账号的使用额度。

账号使用额度可能更快耗尽。

请求集中时，触发限流或安全提醒的风险可能上升。

C9 必须保证任一实例发现账号级限制后，其他实例也停止派单。

特别注意：C9 解决的是限流后的统一收敛，不是提高账号配额，也不是防止所有限流发生。
