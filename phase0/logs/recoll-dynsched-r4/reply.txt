R2-01：AuthCheckContract — PASS

R2-02：额度预留账本 — REWORK

已闭合：

active_count + valid_reserved_count ≤ 3。

RESERVED 立即占用额度。

RESERVED 的终态转换和 reservation_id 幂等释放已有定义。

重启时不再无条件丢弃未提交预留。

未闭合：跨存储原子事务的实现边界。

方案要求同时写入：

scheduler-state.json

workflow_journal

并声称两者与额度变化在同一事务边界提交。但单一 JSON 原子替换只能保证该文件自身的原子替换，不能自然保证另一个独立文件也参与同一事务。

如果先写 JSON 后写 journal，或反过来，中间崩溃仍然可能出现不一致。R4 没有定义如何解决这一窗口。

另外，EXPIRED 的判定条件和有效预留的过期恢复规则也尚未定义清楚。

建议：

明确唯一权威账本和事务提交点。

若采用 journal 驱动恢复，定义 prepare/commit、事务 ID、提交标记和重放规则。

明确 EXPIRED 的触发条件，以及重启时如何区分过期预留和仍然有效的在途任务。

保证任何恢复结果都不会重复释放或重复占用额度。

R2-03：决策持久化前置 — REWORK

DECISION_ACCEPTED 前置于 DRAINING。

明确阶段 2 是不可撤销的用户决策提交点，阶段 6 只是 proposal 流程完成标记，不得再次承担决策提交语义。

R2-04：DRAINING 屏障与 fencing — REWORK

已闭合：

引入屏障时 epoch+1。

在途白名单及采集游标已纳入。

交接完成后 generation 再递增。

所有相关写入口要求服务端校验 fencing token。

未闭合：两个阶段的执行时点存在不一致。

R2-03 的阶段顺序是：

DECISION_ACCEPTED → DRAINING → HANDOFF_READY → VICTIM_RELEASED

但 R2-04 又规定：

阶段 2 完成即 epoch+1，同时置 victim 为 DRAINING。

这相当于在阶段 2 就执行了阶段 3 的动作。需要明确这究竟是阶段 2 的原子副作用，还是阶段 3 的正式状态转换，否则重启恢复时可能出现决策已接受、DRAINING 尚未记录、epoch 却已经变化的状态。

此外，“记录最后可接受的采集事件游标”还需要明确边界：白名单允许的是不超过该游标的事件，还是从当前游标继续到该游标？必须定义事件顺序、重复事件处理和游标之后的拒绝规则。

建议：

统一 R2-03 和 R2-04 的阶段边界，明确决策提交、epoch 递增、DRAINING 状态变更是否属于同一个原子操作。

明确采集游标的上下界和事件去重规则。

明确白名单关闭与 generation+1 的先后顺序，以及旧 token 在服务端失效的准确时点。
