一、先确定 Basic 与中级版的关系

我赞成你提出的总体方向：Basic 不是重新开发一套系统，而是从现有中级版中提取经过验证的基础能力，组合成一个轻量、独立、容易复制的工作流程。

建议明确三个原则：

中级版保留原则：现有 app/、contracts/、phase1/ 不删、不为 Basic 大幅改造，继续作为中级版的基础。

代码复用原则：Basic 可以复制中级版的成熟小功能，但不直接依赖中级版完整运行环境。

独立运行原则：Basic 复制到另一台电脑后，不要求部署中级版的数据库、调度器、服务端或完整治理体系。

Basic 首期不应该为了自动化而增加复杂度。

二、六模块的最小交付方案

我的建议是：首版以文档为主，脚本为辅。六个模块不需要一开始全部编程实现。

1. 任务管理（Task Management）

作用：记录用户提出的需求，建立任务身份和状态。

最小交付物：

TASK-TEMPLATE.md：任务登记模板。

TASK-STATUS.md：任务状态定义。

tasks/：每个任务一个独立目录。

建议任务记录字段：

字段

	

内容




Task ID

	

唯一任务编号




需求描述

	

用户原始需求




验收目标

	

最终需要实现什么




优先级

	

普通/高




当前状态

	

待规划/开发中/验收中/返工/完成




当前步骤

	

当前实施的子任务




最终结果

	

PASS/REJECT

首期：纯文档即可。

不需要数据库，也不需要专门的任务管理服务。

2. 规划协商（Planning & Negotiation）

作用：让规划 AI 与用户形成一致方案，避免开发 AI 自行理解需求后直接写代码。

最小交付物：

PLANNING-TEMPLATE.md

IMPLEMENTATION-PLAN.md

DECISION-LOG.md

基本流程：

AI 分析用户需求。

AI 输出实现方案。

用户与 AI 讨论修改。

AI 更新方案。

用户明确拍板。

冻结本轮实施方案。

这里有一个重要规则：

用户没有拍板，不允许进入正式开发。

首期：纯文档，不需要规划脚本。

3. 开发执行（Development Execution）

作用：按已经确认的方案，逐步完成代码修改。

最小交付物：

STEP-TEMPLATE.md

DEVELOPMENT-LOG.md

CHANGES.md

每一步至少记录：

本步骤目标。

修改文件。

修改内容。

执行结果。

测试结果。

提交给独立验收 AI 的证据。

开发 AI 完成一步，必须停止并交给独立验收 AI。

不能自己宣布自己通过。

首期：人工操作 Git 和运行测试即可。

4. 独立验收（Independent Verification）

作用：由不同的 AI 会话负责验收开发结果。

最小交付物：

ACCEPTANCE-TEMPLATE.md

ACCEPTANCE-RECORD.md

ACCEPTANCE-RULES.md

验收结果只有两种：

PASS：本步骤通过，允许进入下一步。

REJECT：不通过，退回开发 AI。

验收至少检查：

是否符合本步骤目标。

是否符合用户拍板的方案。

修改是否超出范围。

是否存在明显代码质量问题。

测试是否真实执行。

是否有可核查的证据。

首期：人工检查代码、运行测试、记录结论。

5. 返工管理（Rework Management）

作用：控制反复修改，防止 AI 陷入无限返工。

最小交付物：

REWORK-RULES.md

REWORK-LOG.md

建议规则：

次数

	

处理方式




第一次 REJECT

	

开发 AI 修复




第二次 REJECT

	

分析失败原因，调整修复方案




第三次仍 REJECT

	

停止当前循环，召开用户决策会议

这里必须区分：

同一问题的返工次数。

不同问题的验收次数。

不能因为开发 AI 修改了三个不同问题，就误判为同一问题已经返工三次。

第三轮仍无法收敛，必须向用户说明原因、已尝试方案、剩余风险和可选决策，不允许无限循环。

首期：纯文档即可。

6. 交付管理（Delivery Management）

作用：确保开发完成后能够正常使用、追溯和恢复。

最小交付物：

DELIVERY-CHECKLIST.md

FINAL-REPORT-TEMPLATE.md

Git 提交记录。

最终检查：

所有步骤均已 PASS。

整体测试已完成。

没有遗留的未处理 REJECT。

Git 工作区状态符合预期。

已完成 Git commit。

形成完工总结。

完工总结应包含：

原始需求。

最终实现内容。

修改文件。

测试结果。

Git commit。

未解决问题。

后续建议。

首期：人工操作即可。

四、第一个真实闭环验证任务

我建议不要一开始就测试复杂的 Java 业务开发。

先选择一个小型、可验证、影响范围有限的任务。

推荐任务：Basic 任务包完整性检查工具
建议作为首个闭环任务

任务目标

开发一个 Python 标准库小工具，检查一个 Basic 任务目录是否具备完整的任务记录。

具体功能

检查任务基本信息是否完整。

检查是否有用户拍板的实施方案。

检查每个实施步骤是否有独立验收记录。

检查 REJECT 是否有对应返工记录。

检查同一问题是否超过三轮。

检查整体测试和完工总结是否存在。

技术约束

Python 标准库。

不接数据库。

不接 API。

不依赖中级版。

输入一个任务目录，输出 PASS 或 FAIL 及具体缺失项。

配套少量自动化测试。

按你的四步流程完整执行

第一步：用户提出需求

用户提出任务包检查工具需求，规划 AI 整理边界和验收标准。

第二步：规划协商

规划 AI 提出文件结构、输入输出、检查规则和测试方案，讨论后由用户拍板。

第三步：逐步开发与独立验收

开发 AI 每完成一个步骤就交给独立验收 AI。

PASS 才继续；REJECT 则返工。同一问题第三轮仍未解决，暂停并提交用户决策。

第四步：整体测试与交付

使用正常任务、缺少验收记录、超出返工次数等测试数据验证工具。

全部通过后 Git commit，形成完工总结。

为什么选这个任务？

因为它能验证 Basic 六模块之间的配合，同时不会涉及复杂业务代码、外部 API 或中级版运行环境。

还有一个好处：完成后，这个工具可以反过来帮助检查 Basic 自身的任务记录。

五、风险与边界

我认为有七个风险需要在 Basic v0.1 就明确。

风险

	

建议控制措施




Basic 越做越复杂

	

首期人工优先，不提前开发自动化




中级代码依赖过多

	

禁止 Basic 直接依赖中级版运行时




规划 AI 越权开发

	

必须等待用户拍板




开发 AI 自我验收

	

必须使用独立 AI 会话验收




返工无限循环

	

同一问题最多三轮，之后交用户决策




验收证据不可靠

	

验收人独立查看代码、diff 和测试结果




Git 操作造成损失

	

首期人工确认 commit、push，不允许工具擅自推送

Basic 首期明确不做的事情

不做多 AI 自动调度。

不做自动任务领取和派发。

不做数据库和服务端。

不做复杂契约引擎。

不做自动合并分支。

不做无人确认的 Git push。

不承担复杂项目的并行开发。

这些能力属于 Standard 或 Advanced 的发展方向。

还有一个特别重要的边界：独立验收

独立验收不能只是另一个 AI 阅读开发 AI 写的完工总结，然后表示通过。

验收 AI 至少应当拿到：

用户拍板的方案。

本步骤验收标准。

开发前基线 commit。

实际代码修改 diff。

测试执行结果及证据。

由它自己核查。

这是 Basic 能否真正提高开发质量的关键。
