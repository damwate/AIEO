二、两个自查决策点
D1：是否采用显式 CLI？
建议采纳

我支持草案推荐的一期方式：

engineering_audit_leg.py run --batch-id BATCH-001 ...

理由：

当前 M1 没有批次级审计状态机钩子。

自动轮询需要引入触发状态、重复触发、并发控制等额外机制。

GPT-05 当前目标是验证真实审计收发与留证，而不是自动化批次调度。

显式触发容易复现、排查和人工接管。

因此，D1 不需要再保留轮询方案作为一期待决选项。

建议 Gate1 整改时直接明确：

一期唯一触发方式为显式 CLI 指定 batch_id，每次运行对应一轮审计；自动触发另行立项。

D2：artifacts + messages 是否构成权威结论？
架构成立

我支持 GPT-02 路线 B 同构。

没有原生批次审计结论端点，就没有必要为了 GPT-05 改造 M1。

两类记录承担不同职责：

记录

	

职责




审计报告 artifact

	

保存正式结论、完整 findings、风险和证据




AUDIT_SUBMITTED message

	

批次级登记信封、关联审计轮次和报告证据

二者构成完整的结论留证链。

但是有一个重要要求：

必须指定审计报告 artifact 为结论内容的唯一权威载体，message 是登记与关联记录，不得成为另一份独立结论。

如果 message 与 artifact 的 batch_id、audit_round_id、result、SHA 等绑定关系不一致，必须腿级 BLOCKED。

多事务登记也必须保留逐项核验和断点恢复能力，不能假设两个 artifact 与一条 message 原子提交。

这个问题不需要改变总体架构，留 Gate2 明确实现规则即可。
