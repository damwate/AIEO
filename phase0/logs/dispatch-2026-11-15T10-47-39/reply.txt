2. 治理方案
2.1 工作区隔离：优先 Git Worktree

建议 M2 采用：

一任务、一执行会话、一独立 worktree、一任务分支。

合并仍须用户拍板

取舍：

Git Worktree：首选。 每个工作区有独立工作目录和 index，共享 Git 对象库，减少重复 clone。

多 Clone：备用。隔离更直观，但仓库状态和远端同步管理成本更高。

同一工作区开多个会话：禁止作为 M2 并行方式。

每个任务必须登记基线完整 SHA、分支、worktree 路径。禁止两个会话共用同一个工作区或分支。

不允许自动合并、自动 cherry-pick 或无人确认 push。main 合并仍遵循 DEC-010。

2.2 派单锁与排队

phase0/e2e-poc/session_lock.mjs 的全局互斥限制应当保留。

建议：

派单和回复采集采用人工 FIFO 队列。

高优先级任务允许明确插队，但记录原因。

每次派单核对 task ID、dispatch ID、conversation UUID。

每次回复核对 request/reply 原始字节及 SHA256。

不允许通过并发启动多个派单来绕过锁。

这里需要区分：

派单串行，不等于开发串行。

派单完成后，多个独立开发会话可以同时在各自 worktree 工作。

2.3 开发会话与验收会话

采用以下纪律：

开发会话不得跨任务复用。

验收会话不得与对应开发会话混用。每个任务仍执行现有 WORKFLOW 的六查、PASS/REJECT/BLOCKED 规则。

由于派单采集是单通道，验收派单与回复采集仍然串行。

2.4 优先级和冲突管理

不建议增加复杂优先级算法。

沿用现有任务书的高/普通两级，增加以下管理约束：

每个任务登记依赖任务。

每个任务声明负责修改的文件或目录。

同一文件同一时段只能有一个任务写入。

公共工具、WORKFLOW、decision-log、模板和全局配置默认视为独占资源。

前置任务必须 PASS，依赖任务才能进入相应开发步骤。

发生冲突时：

相关任务停止写入。

记录 BLOCKED 和冲突原因。

指定一个整合责任人。

重新协商修改范围和解决方案。

重新进入独立验收。

不得靠覆盖文件或盲目 rebase 消除冲突。

4. 分步实施建议

第一阶段：继续 M1

使用现有 v0.3 挂起和并行机制，不改变当前工作流程。

第二阶段：建立 M2 规则

形成治理文档，经过复审和用户批准后再生效。

第三阶段：小规模实战

最多两个并行任务

选择低冲突、互不依赖、文件所有权清晰的任务。各自使用独立 worktree、分支和会话。

第四阶段：复盘

至少观察一轮完整闭环，重点统计：

工作区污染次数

文件及分支冲突次数

派单归属错误次数

验收会话串用次数

并行节省时间与额外管理成本

第五阶段：决定是否扩大

根据实战证据决定是否扩大并行数量、固化模板字段。M3 必须另行讨论。
