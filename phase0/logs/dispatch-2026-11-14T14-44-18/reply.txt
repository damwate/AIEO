特别强调三个问题：

1. 不能把占位符当成有效内容。

例如：

纯文本

- 验收标准：TODO

这些虽然非空，但不代表有效记录。

2. 不能只检查文件里出现过 PASS。

必须将 PASS 关联到具体步骤，避免一个步骤的 PASS 被错误地当成所有步骤通过。

3. 不能只检查存在 REJECT。

必须建立问题编号、REJECT记录和返工记录之间的关联。

首期不要求 AI 理解自然语言是否真正合理，但必须保证结构和记录之间的可追溯性。

Q3：落位和判定规则还有什么漏洞？

我有六项建议。

1. 文件路径和任务包边界
建议采纳

落位：

纯文本
basic/
└── tool/
    └── check_taskpack.py

合理。

但需要明确：

检查对象必须是指定任务目录。

不允许默认检查当前工作目录。

必须检查关键文件是否位于任务包根目录。

不允许通过目录外文件补足任务包缺失记录。

2. 六项检查必须相互独立

不要写成一个巨大的检查函数。

建议：

Python
运行
check_requirement()
check_steps()
check_step_acceptance()
check_rework_records()
check_rework_limit()
check_delivery()

每个函数返回结构化检查结果。

这样未来增加检查项，不需要重写整体逻辑。

3. 返工次数的定义必须明确

建议：

以问题编号作为统计单位。

同一问题连续 REJECT 的返工次数累计。

不同问题分别统计。

同一问题返工超过3次，FAIL。

第3次仍未通过，不允许通过修改问题编号规避限制。

这里还有一个必须明确的边界：

第3次返工之后仍然 REJECT，应该判定为超过允许的三轮处理上限，进入升级处理，而不是允许第4轮继续循环。

4. 证据引用不能只检查文字

例如：

纯文本
证据：test_result.txt

如果文件不存在，这个证据引用实际上没有意义。

建议首期至少支持：

任务包内部相对路径。

Git commit SHA。

测试命令及其结果记录。

其中，内部文件引用应检查目标文件真实存在，禁止路径穿越到任务包外部。

Git SHA 和命令记录则先检查格式及内容，不要求工具自动执行全部测试。

5. CLI输出必须方便其他AI读取

建议输出：

纯文本
Taskpack: b-20261114-taskpack-checker
Phase: IN_PROGRESS

[PASS] ① 需求记录
[PASS] ② 步骤清单
[FAIL] ③ 步骤验收记录
[N/A] ④ REJECT返工记录
[PASS] ⑤ 返工次数
[N/A] ⑥ 交付记录

Overall: FAIL
Exit code: 1

注意：这里的 FAIL 表示开发阶段已有步骤的记录不完整，而不是因为尚未交付。

建议额外支持：

Bash
python check_taskpack.py <task_dir> --json

输出机器可读 JSON，方便规划 AI、执行 AI 自动读取检查结果。

6. 必须增加异常输入测试

现有测试方案基本正确，但还缺少以下场景：

任务目录不存在。

关键文件缺失。

文件编码异常。

空文件。

字段重复。

步骤编号重复。

步骤验收记录与步骤清单不对应。

证据引用不存在。

非法任务阶段。

同一问题第3次和第4次返工。

路径穿越。

这些比单纯测试几个正常和异常样例更有价值。
