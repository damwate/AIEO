R4 的三项整改在文档层面基本落实：SQLite 唯一权威存储、事务挂起边界如实披露、C1–C7 已替换为 SQLite 专项矩阵。R4 原有的“挂起期间其他写者正常推进”错误表述已删除。

但 R5 仍有事务协议的关键缺口，尤其是并发首写路径和提交失败后的事务清理。它们会影响账本正确性及后续写者能否继续工作，因此不能授予设计 PASS。

阻断项
P0-1：并发首写竞态的处理路径不成立

§2 第1步规定：事务外查询无该行，走 INSERT 路径。

但第5步又规定：changes==0 且行不存在，判定为并发首写竞态，重走 INSERT 路径。

这里存在 SQL 语义问题：

假设 A、B 同时读取，均发现 UUID 不存在。

B 先取得写事务资格并成功 INSERT、COMMIT。

A 随后取得写事务资格，再执行普通 INSERT。

A 遇到的是 PRIMARY KEY 唯一约束冲突，通常是 SQL 异常，不是 changes==0。

因此，文档所写的“并发首写竞态通过 changes==0 识别”不能覆盖实际路径。

整改要求：

明确首写 INSERT 的冲突处理，例如捕获指定的主键唯一约束冲突，再重新读取账本并进入已有行的 gen 条件更新路径。

不得把所有 SQLITE_CONSTRAINT 都当成并发首写冲突。

增加两个独立进程同时首次写入同一 UUID 的测试，断言两轮数据都被正确累计，不能丢失其中一轮。

这是数据正确性阻断项。

P0-2：COMMIT 失败后的事务状态没有定义

§2 第5步规定 COMMIT 失败时如实上抛，但没有定义失败后连接和事务如何清理。

SQLite 中，某些 COMMIT 失败（例如遇到 BUSY）时，事务可能仍然处于活动状态，并不意味着自动回滚。

如果直接上抛并复用连接，可能出现：

连接仍持有未完成事务；

后续操作遇到事务状态异常；

写锁继续被持有，其他进程持续等待；

原本可恢复的错误扩大成账本不可用。

整改要求：

明确 COMMIT 失败后的事务状态检查和清理策略。

在可回滚的情况下显式 ROLLBACK。

如果回滚也失败，废弃该连接，不得继续复用。

明确提交结果不确定时的处理方式：不得直接把本轮计数当作成功，也不得盲目重放导致重复累计。

增加 COMMIT 失败及连接清理测试。

这项是事务生命周期的完整性要求。

P1-1：busy_timeout 与重试策略存在冲突

§1 设置 busy_timeout=5000ms，§2 又规定 SQLITE_BUSY 后重试 3×500ms。

两个参数的关系没有定义清楚：

如果每次 SQL 操作内部已经等待 5000ms，外部再重试 3 次，实际等待时间可能远超预期。

如果预期总等待约 1500ms，则 5000ms 的 busy_timeout 与该目标不一致。

**整改要求：**统一等待预算，明确 busy_timeout 是单次等待上限还是整个操作的总等待期限；给出可验证的最大等待时间，避免调用方误以为 3×500ms 就是总时限。
