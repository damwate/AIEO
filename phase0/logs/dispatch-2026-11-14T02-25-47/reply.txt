三、建议增加的六项要求

F-01：输入与执行安全

这是当前任务书最明显的缺项。

必须明确：

worktree 必须存在且是有效 Git 工作树。

指定 commit 必须是完整 40 位 SHA。

Worker 必须核对 worktree 实际 HEAD 与指定 commit 一致。

命令使用 argv 数组执行，禁止 shell=True。

每条命令固定工作目录，不能自行改变 Worker 的执行根目录。

超时、命令不存在、进程启动异常均应有明确失败结果。

禁止命令清单通过任意 shell 字符串执行。

特别是不能让 Worker 变成一个不受限制的任意命令执行入口。

F-02：测试执行结果必须具有明确语义

冻结 Schema 有两个不同字段：

字段

	

允许值

	

含义

EXECUTED_PASS / EXECUTED_FAIL / NOT_EXECUTED / CLAIMED_ONLY / BLOCKED

	

执行事实




result

	

PASS / REWORK / BLOCKED

	

任务验收结论

建议明确映射：

所有命令真实执行且成功：EXECUTED_PASS + PASS

命令真实执行但存在非零退出：EXECUTED_FAIL + REWORK

未能启动执行或执行被阻断：BLOCKED + BLOCKED

未执行：不能伪装为执行成功。

这里尤其需要强调：Worker 自身运行成功，不代表被测项目测试通过。

F-03：日志与报告必须互相对应

报告 payload 中保存对应日志的相对路径及 SHA-256，使审查者可以从报告追溯到原始证据。

F-04：失败处理策略必须确定

目前任务书规定不重试，但没有明确一条命令失败之后如何处理后续命令。

建议最小版：

顺序执行。

不自动重试。

记录每条命令的真实结果。

明确采用继续执行剩余命令还是停止执行的策略。

超时和异常不得被记录成普通成功。

整体状态根据实际执行结果计算，不允许人工覆盖。

建议把这条作为实现前的明确约束。

七、我对 F-003 的额外判断

我认为 F-003 应当坚持一个非常重要的设计原则：

Worker 只负责提供事实，不负责宣布事实是否可信。

具体来说：

Worker 负责真实执行。

Worker 负责保存原始证据。

Worker 负责生成结构化报告。

Schema 负责检查报告结构。

独立审查者负责判断证据是否足以支持验收。

用户负责最终授权。

这样才能避免未来出现 Worker 自己执行、自己判断、自己宣布 PASS 的闭环漏洞。

这也是 F-003 与未来 F-001 调度系统之间应该保持的职责边界。

会务最终建议：采用 T-P1-907 + 独立 CLI + REST 方案 B，补充上述六项要求后形成 v0.2，重新提交会务确认。
