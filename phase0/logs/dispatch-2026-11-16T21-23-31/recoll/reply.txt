① A-1：运行期白名单
REJECT

关键证据：

app/platform/api.py，blob 62a8c60c1902f1771776bda1d5094f7b23b24477，第 304–316 行：确实存在 GET /api/v1/tasks，支持 batch_id、分页及 total。

app/platform/security.py，blob 7b1efc8db8d22327aeeb81de5b9dfdf7f73e0e31，SERVICE_ALLOWED_ENDPOINTS：允许 GET /api/v1/tasks/{task_id}，但没有允许 GET /api/v1/tasks。

同一权限表已允许 GET /api/v1/reports、POST /api/v1/artifacts、GET /api/v1/artifacts/{artifact_id}、POST /api/v1/messages。

因此，ENGINE-04 使用服务身份执行 GPT-05 的核心前置读取时，会被服务端权限门拒绝。即使 GPT-05 客户端白名单写得正确，也无法绕过服务端授权。

这是开工阻断项。 不能用 OWNER 用户凭据代替 ENGINE-04 服务身份，也不能默默放宽 M1–M4 零修改红线。

此外还有两个需要在 Gate2 方案中明确的点：

当前服务端白名单是所有 service agent 共用的集合，并非 ENGINE-04 专属权限表。必须明确 ENGINE-04 身份验证、token 绑定及客户端 method/path 默认拒绝如何共同形成有效边界。

GET /reports 支持 type、task_id 过滤；应按批次任务逐项查询，而不能假设它有 batch_id 过滤。

尚未冻结的内容：

engineering_standard_version 目前只是批次字段绑定；没有明确七项规范清单对应的不可变文件路径、版本和 SHA256 清单。

release_recommendation 与总 result 的映射已定义方向，但契约层应固定每一种组合的合法值，不能只靠自然语言审查。

report artifact 与 AUDIT_SUBMITTED message 的完整 payload 绑定结构尚未定稿。尤其要明确报告 artifact SHA、brief SHA、reply SHA、manifest SHA 各自含义，避免同一个 SHA 字段被不同对象复用。

message 的 source_agent_id、target_agent_id、correlation_id、payload 与 ENGINE-04/GPT-05 身份的对应关系需要固定。现有 messaging.register_inbound_message 检查 source/target agent 是否存在，但没有把消息 source 与认证 principal 做相等性绑定。

补齐要求： Gate2 定稿应给出字段级契约表及 message envelope 示例，并明确每个 SHA 的对象、计算范围、生成时点和交叉核验规则。七项规范必须绑定不可变版本清单，而不只是一个版本字符串。

③ A-3：恢复矩阵
REJECT

依据： v0.3 附录 A-3 目前只有断点、恢复动作、是否允许重新派单三列。

它列出了简报前、简报后、发送意图未确认、已发送未采集、已采集未登记、登记部分成功、登记完成等状态，但缺少实际可执行的恢复账本定义。

尤其是登记部分成功：目前只写 _ledger_verified 逐项只读核实补缺项，没有明确两份 artifact 和一条 message 各自对应的账本标志、证据核验和恢复动作。

补齐要求： 每个断点至少固定：

必须存在的账本标志及其字段；

用于确认该步骤真实成功的 M1 读回证据；

允许执行的唯一恢复动作；

明确禁止的重派、重登记或覆盖动作；

操作完成后应追加的账本标志；

证据不完整或相互矛盾时的 fail-closed 结果。

特别要将两个 artifact 和 message 拆成独立登记步骤，不能只用一个笼统的 A4_REGISTERED 标志代表三项均成功。

REJECT

固定代码事实：

app/platform/reports.py，blob a4451d7094c04615da42dc193bdadfbeb84085ec：register_artifact 按 path 唯一；相同 SHA 返回 duplicate，不同 SHA 冲突。

设计缺口：

没有冻结两份 artifact 与 message 的精确登记顺序。

没有将三项登记拆成三个独立的 ledger 标志和读回核验。

没有明确 artifact duplicate 的读回核验条件，以及 message 409 后如何通过 correlation_id 读回并比对完整 envelope。

A-1 未把 GET /api/v1/messages 纳入 GPT-05 运行期客户端白名单。它是核实 message 是否已登记、验证 409 和恢复部分成功的重要接口。

message_id 确定性键没有给出生成规则。必须确保同一审计轮重放得到相同 ID，不能因为恢复而生成新 ID。

账本请求指纹需要定义规范化算法和字段覆盖范围；不能只比对 message_id 或本地记录。

补齐要求： 固定三项登记顺序、每项成功标志、M1 读回字段、duplicate 判定、409 双证以及每种部分成功组合的恢复动作。登记过程中禁止新开审计轮或重新派单。
