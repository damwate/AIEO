但这里要区分两个概念：

配置权威性： 注册表优先，因为 SakuraCat 会在重启时更新系统代理端口。

运行可用性： 实测连接结果优先，注册表中的端口不代表服务一定正常。

例如：

注册表记录 3572，但 SakuraCat 已退出，3572 不再监听。

此时不能因为注册表有值就认定代理可用。

反过来，如果注册表仍是 3572，但实际监听已经迁移到 2482，也不能盲目坚持使用 3572。

建议确立规则：

注册表提供首选候选端口。

实际监听和 HTTP/HTTPS 探测验证端口。

注册表端口失效时，继续检查其他候选来源。

不得将配置存在等同于端口可用。

另外，注册表 ProxyServer 必须按协议解析。

例如：

纯文本
http=127.0.0.1:3572;
https=127.0.0.1:3572;
socks=127.0.0.1:3572

不能简单使用字符串整体提取第一个数字，也不能假设所有协议端口相同。

Q2. check-push 候选序列

建议采纳你的顺序：

直连测试

先判断是否存在无需代理的可用路径。

注册表 ProxyServer

读取当前系统代理，按协议提取候选地址和端口。

git config

读取 Git 遗留代理配置，作为兼容性回退。

netstat 监听端口

最后发现其他可能的代理监听端口，逐一验证。

我建议再增加三个约束。

约束一：所有候选端口必须经过真实探测。

不能只检测 TCP 端口是否监听。

建议使用目标 GitHub HTTPS 地址进行实际代理请求，验证：

TCP 连接成功；

TLS 握手成功；

HTTP 请求获得预期响应；

最终 Git 推送能够成功。

其中 HTTP 200 是本次实际验证成功的证据，但不能把 HTTP 200 设为所有探测请求的唯一成功条件。例如 GitHub 某些接口可能返回 401、403 或 404，这些响应仍然能证明网络和 TLS 链路已经建立。

约束二：避免过期端口污染。

如果注册表、git config、netstat 得到相同端口，应当去重。

如果注册表端口失败，不要直接停止；继续尝试其他候选。

同时记录端口来源和失败原因，避免最后只输出一个模糊的「代理不可用」。

约束三：只读原则必须严格执行。

check-push 不应：

修改 Windows 注册表；

修改 Git 全局代理；

修改系统代理；

自动重启 SakuraCat；

将探测成功的临时端口写回配置。

它的职责是发现、验证、使用，而不是接管代理配置管理。

特别建议：netstat 发现的端口不一定属于代理软件，也可能是其他本地服务。因此必须经过代理协议探测，不能直接把监听端口当代理。

诊断工具执行失败、返回空值或异常结果时，不得直接据此认定目标资源不存在。必须先核实调用环境、命令参数、Shell 转义、参数兼容性、权限和输出解析方式。至少通过一种独立方式交叉验证后，才能作出不存在或不可用的判断。

这条原则不只适用于 Windows 注册表，也适用于 Linux、Git、网络、进程和文件系统诊断。

最终建议：本次讨论形成的设计原则

我建议将以下五条作为本次共识：

注册表 ProxyServer 是 Windows 系统代理的首选发现来源，按协议解析。

直连 → 注册表 → git config → netstat，是 check-push 的候选发现顺序。

配置来源只负责提供候选，实际连接测试负责判定可用性。

check-push 严格只读，不擅自修改代理、Git 或系统配置。

诊断工具失败必须区分调用失败与资源不存在，必要时交叉验证，禁止未经验证直接下结论。

额外建议： 将端口发现和端口验证拆分成两个独立逻辑模块。未来更换 SakuraCat 或其他 VPN 客户端时，只需要调整发现适配器，不必重写 Git 推送恢复逻辑。

这样才能让 check-push 从一次性故障修复脚本，逐步成为可迁移、可维护的基础工具。
