二、P0 阻断：记账失败没有形成可持续的 UNCERTAIN 状态

文件： phase0/tools/gpt_dispatch.mjs
复核依据： 指定 SHA 下该文件的实际内容，blob SHA 6273763e19a5ff18e3397bddcde2f1d6069ff66b。

发送确认后的 recordInOnce()：

调用 recordTurn() 记 input；
成功才设置 inBytesRecorded = true；
失败时只写 WARN 日志，继续派单流程。

回复采集完成后的 output 记账也采用相同处理：`recordTurn(... completeOpenTurn: true)` 失败后只记录 WARN，不把当前会话转入持久的 UNCERTAIN 状态。

这与设计约束不一致：设计明确要求 BUSY 超时等记账异常由调用方转 UNCERTAIN、fail-closed；UNCERTAIN 不得自动放行。

具体风险场景：

发送已确认，input 记账因 LEDGER_BUSY_TIMEOUT 失败。
当前代码只告警，派单仍继续。
下一次预检时数据库已恢复，`assessLedger()` 可以正常读取旧账本。
旧账本没有本轮 input，预检可能仍返回 NORMAL 并允许继续发送。

即使数据库没有损坏、下一次读取完全成功，账本也可能是陈旧但看似正常的。因此“下次预检按 UNCERTAIN fail-closed”的日志说明并没有对应的状态机制来保证。

output 记账失败也有类似问题：本轮 output 未计入，`open_turn_bytes` 可能遗留；而 assessLedger() 的预算判定只看 total_bytes，不会因为未完成轮次自动转 UNCERTAIN。

整改处方：

发送确认后的 input 记账失败，必须使该会话进入可被后续预检读取的持久 UNCERTAIN 状态；不能只靠日志。
COMPLETED 阶段 output 记账失败，同样必须保留 UNCERTAIN，不得让后续预检把旧累计值当成完整账本。
预检遇到 UNCERTAIN 必须拒发，直到有明确、可审计的恢复/核对流程解除。
增加故障注入测试：分别模拟 input 记账失败、output 记账失败；随后恢复数据库，再执行预检，必须仍拒发，不能回到 NORMAL。

这是发送已经发生、账本却可能漏记，后续仍自动放行的问题，属于 P0。
