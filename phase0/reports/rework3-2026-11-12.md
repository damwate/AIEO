## 1. 问题确认与修复

### 审查指摘（确认属实）

R2 中 `tailOk` 与 `stopOk` 是两个独立闩锁：`stopOk` 可先于本轮 user 消息确认而置位，随后经 `initialObserved: stopOk` 将历史生成状态注入本轮 `generationObserved`；且 `trackGeneration` 在首次观察到 false 时即置 `generationEnded`，两者叠加无法严格证明观察到的是**本轮消息对应**的生成状态。R2 场景 1 恰好把该时序当作成功路径，未覆盖异常序列。

### 修复（实际代码）

**新增 `verifySendAcceptance()`（`phase0/e2e-poc/completion_judge.mjs`，生产与测试同源）：**

- 严格时序语义：
  1. `tailOk`：本轮 user 消息确认出现在 DOM（尾部 unit 前进且 role=user）；
  2. `stopOkAfterTail`：**仅在 tailOk 确认之后**的轮询中观察到停止按钮可见才置位——这是 `generationObserved` 的**唯一**初始化来源；
  3. tail 确认前的停止按钮观察记入 `stopSeenBeforeTail`（**只记录、不采用**，供审计）；
  4. `deadlineMs`（30s）内未同时满足 → `accepted=false` → 调用方按 UNCERTAIN 抛错终止（不重发，fail-safe）。
- `e2e_orchestrate.mjs` `sendAndCollect`：删除旧的双闩锁循环，改用 `verifySendAcceptance`；tracker 初始化改为 `initialObserved: acceptance.stopOkAfterTail`。
- 判定结果全量写入结构化 evidence：`e2e-evidence.json → steps[n].send_acceptance`（tail_ok / stop_ok_after_tail / stop_seen_before_tail_excluded / polls）。

### 时序语义对照

| 时序 | R2 行为 | R3 行为 |
|---|---|---|
| 停止按钮先于 user 确认出现（历史状态） | stopOk 置位 → 污染 generationObserved | 记录 `stopSeenBeforeTail` 并**排除**，不参与初始化 |
| user 确认后观察到停止按钮 | （不区分） | `stopOkAfterTail=true` → 唯一合法的 generationObserved 来源 |
| user 确认后停止按钮始终未再出现 | （不发生此分支） | `accepted=false` → UNCERTAIN → exit 1，不误判成功 |
