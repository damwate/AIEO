## 1. 根本性设计变更：锁 v6 —— 放弃一切内容仲裁，改用 OS 句柄

### 审查指摘（确认属实）

v5 的死票据清理仍是"读票据 → 判死 → unlink"的 check-then-act：A、B 同时读到同一张死票据 T，A 删 T 建 T_A，B 按旧读 unlink 掉 T_A → 双回收者 → 双持锁可能。测试未覆盖该交错。

### 修复：v6 协议（`session_lock.mjs` 彻底重写）

**洞察：v1~v5 的全部竞态都源于"以文件内容为竞争判定依据"。v6 让内容彻底退出判定**：

- **持锁 = 进程持有锁文件上的 FileShare.None 独占句柄**（Windows 内核原子裁决，不可伪造、不可竞争）；
- **竞争 = 他人以 FileShare.None 打开同一文件 → 内核共享冲突 → fail-closed 拒绝**（无任何内容判定路径——v1~v5 的初始化窗口/空文件/坏 schema/死票据 TOCTOU 各竞态在本设计中**无存在路径**）；
- **持有者死亡 = 句柄由内核随进程终止自动释放** → 后来者直接**接管同一文件**（OpenOrCreate 成功 + 覆写审计内容）——**全程无 unlink**（unlink 仅不存在于任何路径）；
- 实现：PowerShell 守护子进程持有句柄（Node 无法设置 Windows 共享模式），父进程死亡 → 守护进程 ≤500ms 自行退出（句柄释放，无孤儿锁）；
- 锁文件内容仅作审计（holder pid/rand/born_at），**从不参与竞争判定**；
- release = 向守护进程 stdin 写信号 → 守护进程关句柄退出（≤3s 兜底 kill）。
