## 1. MAJOR-1：rename 换出非 CAS —— v4 协议（tombstone 确定性票据 + unlink 前世代复核）

### 审查指摘（确认属实，复述确认）

v3 中"回收者 A 读到 S → 暂停 → 回收者 B 换出 S 并创建新锁 N 持锁 → A 恢复执行 rename 会把 N 整体移走"；世代验证只能发现破坏不能撤销；随后 C 可创建 → B、C 双重持锁。"迟到回收者只会遇到 LIVE 或 ENOENT"的论断不成立。

### 修复（`session_lock.mjs` v4）

**放弃 rename 换出**。回收改为「确定性命名票据 + unlink 前世代复核」两步（拆分为导出函数 `createReapTicket` / `completeReap`，生产与测试同一实现，无测试钩子）：

1. **票据**：`tomb-<S.rand>.json`——名字由目标世代 S 的内容唯一决定，wx 原子创建 → 同一世代全协议**最多一个存活回收者**；票据被存活者持有时 fail-closed 拒绝；持有者死亡 → 清理死票据重建（对死亡票据的 unlink 无竞争危害）；
2. **unlink 前世代复核**（`completeReap`）：重读锁路径——
   - 内容与 S **全等**（rand+pid+born_at 三元组）→ unlink（移除的正是被票据锁定的世代）；
   - 锁文件已消失 → `vanished`（零改动）；
   - **世代已变（他人已完成回收并可能持新锁）→ `changed`，绝不 unlink**，放弃回收回到主循环。
3. **协议内安全性论证**：S 存在于锁路径期间，任何进程的 wx 创建必然 EEXIST（创建不可能发生）→ 唯一回收者 unlink 时锁路径上仍是 S。"身份检查与移除"由「原子票据（单回收者）+ 复核（世代绑定）+ 协议内无并发创建」三重绑定——不依赖 rename-after-check。
4. **如实声明的理论边界**：若外部违反协议（人工/越权进程在 S 存在时强行写锁）且恰落在"复核与 unlink 之间"的微秒窗口，仍可能误删——这是无 CAS-delete 原语的文件锁理论边界；屏障测试（S7）证明协议内该交错被正确处置（见下）；彻底消除需 OS 级字节锁（LockFileEx / native 模块），列 Phase 1 评估项。

## 2. MAJOR-2：屏障交错测试（审查点名）—— 已新增并通过

`test_session_lock_v4.mjs` S7 为**真实多进程屏障测试**，强制制造审查指摘的交错：

```text
1. 父进程写 stale 锁 S（死 PID）
2. 子进程（回收者 A）：createReapTicket(S) 成功 → 写 marker 暂停（屏障）
3. 父进程模拟"并发回收者 B 完成"：在锁路径写入新活锁 N（holder=父进程存活 PID）
4. 父进程放行（go 文件）
5. A 的 completeReap 复核 → 世代已变 → outcome="changed"，未 unlink
6. 断言：N 字节级留在 lockPath（A 不得移走它）；
        第三进程 C（模拟）在 N 存活期间 acquire → SESSION_LOCK_CONFLICT（C 不得获取）
```

实测：`outcome=changed；N 字节级不变；C 获取冲突` —— 与审查要求的断言一一对应。
