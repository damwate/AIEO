## 0. 文档定位与维护规则

### 0.1 与其他治理文件的关系

1. 本文是**开发经验、失败记录和问题升级机制**，不是公共契约，也不能替代验收。
2. 公共接口与数据契约以 `docs/phase1/platform-contract-v1.0.md` 为准；不得通过修改本文变相修改冻结契约。
3. 架构与治理决策以 `docs/phase1/decision-log.md` 为准；本文引用决策，不自行创造新决策。
4. 会话交接使用 `docs/phase1/handoff-template.md`；独立审查使用 `docs/phase1/review-protocol.md`；主会话与子 Agent 的职责边界使用 `docs/phase1/agent-contract.md`。
5. ChatGPT 网页派单的 ego-browser 细则以 `chatgpt-web-dispatch` skill 所指向的 `references/EGO-LITE-HANDBOOK.md` 为唯一真源。本文只沉淀项目级经验，不复制维护另一份参数手册。
6. 若本文与仓库实际代码、冻结契约或更新后的原始证据冲突，应停止沿用本文相应经验，标明冲突并提交修订；不得选择对当前任务更有利的口径。

### 0.2 何时必须更新

每次开发任务结束时，无论成功、失败还是阻塞，都必须更新本文。以下节点不得等到任务收尾才补记：

- 完成一个 Phase、重要子任务或关键 Commit；
- 公共接口、数据结构、模块职责或模块契约发生变化；
- 重要测试通过、失败，或发现测试证据无效；
- 同一问题发生连续返工；
- 发现架构缺陷、公共契约错误、安全风险或数据丢失风险；
- 会话迁移、审查会话轮换或需要其他 AI 接手；
- 原经验被新证据推翻，或原来的 `BLOCKED` 已具备解除证据。

### 0.3 怎样维护

1. **失败历史只追加、不抹除。** 更正错误时追加更正说明、日期和证据；可以将旧条目标为 `SUPERSEDED`，但不能删除失败过程。
2. **每条经验绑定证据。** 尽可能写明 Task ID、模块、分支、完整或短 Commit SHA、文件路径、测试命令、原始日志和独立审查回复。
3. **事实、决策、待确认、假设分开写。** 根因未直接证实必须使用 `HYPOTHESIS`，不能写成 `CONFIRMED`。
4. **记录真实范围。** 本地测试、依赖注入、真实 Chrome、本地仿真 DOM、真实 ChatGPT、公开 GitHub、私有仓库必须分别标注，不得互相替代。
5. **原始材料落盘。** 长日志、完整回复、Diff 和截图保存到对应证据目录；本文只保留路径、hash/尺寸和必要摘要，不把长原文塞进主上下文。
6. **一次运行一个证据目录。** 推荐 `<logs-root>/<run_id>/`，同一 `run_id` 下保存命令、环境、被测 SHA、stdout、stderr、结构化结果、退出码和审查材料；禁止固定文件名覆盖不同运行。
7. **秘密不入文、不入 Git。** Cookie、Token、Authorization、API Key、完整浏览器 profile、真实账号配置及含隐私的原始页面不得进入本文或公开交接材料。
8. **文档不预写自身 Commit SHA。** 本文提交后的实际版本由 `git log -- docs/AI-DEV-LESSONS.md` 确认，避免自引用哈希不可能成立的问题。

### 0.4 状态与证据口径

| 状态 | 本文含义 | 禁止误读 |
|---|---|---|
| `PASS` | 指定范围内的验收项均满足，且证据充分 | 不等于其他场景也通过 |
| `PASS_WITH_CONSTRAINTS` | 仅在明确列出的范围内放行，约束仍是强制门禁 | 不等于全面验收或允许合并 main |
| `FAIL` | 已执行并明确失败 | 不得包装成“基本完成” |
| `REWORK` | 独立审查发现必须修复的问题 | 修复产生的新 Commit 必须重新审查 |
| `BLOCKED` | 证据不足、环境/权限不足或前置条件不满足，无法核实 | 不得当作 PASS，也不一定等于代码已证明有错 |
| `UNCERTAIN` | 状态无法确定，例如发送后进程退出、缺少完成证据 | 不得自动重发或宣称成功 |

补充规则：

- 测试执行状态沿用 `EXECUTED_PASS / EXECUTED_FAIL / NOT_EXECUTED / CLAIMED_ONLY / BLOCKED`；只有自述没有证据属于 `CLAIMED_ONLY`。
- “负例测试 PASS”表示系统**正确拒绝了坏输入/坏状态**，不表示该业务场景成功。
- “真实 Chrome + 本地仿真 DOM”不等于“真实 ChatGPT”；“脚本正常结束”不等于“验收 PASS”。
- 审查 PASS 必须绑定实际 `reviewed_commit`。后续修复 Commit 不自动继承旧 PASS。
- Phase 0 的 `dispatch-*` 目录名使用 UTC 时间；Git Commit 展示通常使用 UTC+8。记录时必须注明时区，不能把日期差异误判为不同事件。

### 0.5 经验适用范围与有效性标签

**scope:** GLOBAL  
**status:** ACTIVE

每条 `L-xxx` 经验必须同时具有 `scope`、`status` 和 `验证结果` 三类信息；三者不得混用。

**`scope` 适用范围标签：**

| 标签 | 含义 | 使用约束 |
|---|---|---|
| `GLOBAL` | 可适用于所有 AI 协作项目的通用原则 | 只能包含已脱离特定项目参数仍然成立的规则 |
| `AIEO` | AIEO 项目专项规则、参数、标识或证据范围 | 不得直接复制到其他项目作为全局约束 |
| `TOOL_SPECIFIC` | 特定 AI 模型、开发工具、浏览器或库的经验 | 工具升级或更换后必须重新验证 |
| `ENVIRONMENT_SPECIFIC` | 特定 OS、网络、账号或运行环境的经验 | 换环境后不得默认继承结论 |

- 一条经验可以有多个 `scope` 标签，但必须写明哪部分是原则、哪部分是项目/工具/环境细节。
- 示例：不得重复无效修复是 `GLOBAL`；AIEO 的 1200 UTF-8 字节限制是 `AIEO`；PowerShell `FileShare.None` 是 `TOOL_SPECIFIC + ENVIRONMENT_SPECIFIC`。其他项目或环境（例如 Linux Sakura VPN 的检测间隔）必须在自己的经验库中单独记录，不得由本文推定参数。

**`status` 经验有效性标签：**

| 标签 | 含义 | 处理要求 |
|---|---|---|
| `ACTIVE` | 当前有效，可在声明的 scope 内作为工作指导 | 仍需遵守对应验证结果和证据边界 |
| `NEEDS_VALIDATION` | 候选经验，尚待验证 | 不得作为已验证规则强制执行 |
| `SUPERSEDED` | 已被新方案替代 | 保留历史、替代原因、新方案链接和 Commit |
| `INVALID` | 已被证据证明失效 | 禁止继续作为工作指导，但保留失败档案 |

`PASS/FAIL/BLOCKED` 描述某项验证或审查结果，`ACTIVE/NEEDS_VALIDATION/SUPERSEDED/INVALID` 描述经验当前能否使用；`PASS` 不自动等于 `ACTIVE`，`BLOCKED` 也不自动等于 `INVALID`。经验变化时追加替代原因、证据和新方案，不直接抹掉历史。

## 1. 每个任务的标准闭环

**scope:** GLOBAL（流程原则）；AIEO（仓库路径、审查角色与契约引用）  
**status:** ACTIVE

### 1.1 开工前

1. 阅读本文件，搜索相同模块、相同错误码和相同根因；**已证实无效的方案不得原样重试**。
2. 核对当前分支、`base_commit`、工作区状态、任务允许修改范围和冻结契约版本。
3. 把验收标准写成可判定条目，预先确定需要真实环境、仿真、负例、并发或故障注入中的哪类证据。
4. 若任务依赖前一会话，先读取仓库交接包并实查 Git，不把聊天记忆当作事实。
5. 涉及网页发送、外部仓库推送或其他对外动作时，先确认授权、目标和敏感信息边界。

### 1.2 开发中

1. 先复现并定位根因，再修改；优先消除一类系统性问题，不按单个表象堆特殊分支。
2. 每次方案变化都记录“与上一方案的本质区别”，不能只改错误码、变量名或等待时间后称为新方案。
3. 测试必须覆盖已知的反例和交错；独立审查指出的反例应转化为回归测试。
4. 代码变化后重跑受影响测试，并生成新的 Commit 与证据包；旧审查结论随即失效。
5. 公共契约、架构或安全问题不按普通返工处理，立即升级，见 §2.4。

### 1.3 收尾时

1. 按 §6.1 追加任务记录，按 §6.3 输出固定七项汇报。
2. 对照验收标准逐项列证据，明确未执行项和未验证范围。
3. 核对 `git status`、实际 Commit、测试日志中的被测 SHA 和交付包是否一致。
4. 需要独立审查时，由主会话准备启动简报；子 Agent 不直接对接 GPT 审查会话。
5. 触发第三次失败或提前升级条件时，停止修改并生成 §6.2 的独立 AI 审查交接报告。

## 2. 连续返工止损机制

**scope:** GLOBAL  
**status:** ACTIVE  
**决策依据：** 用户与 GPT 独立审阅明确要求该机制作为所有 AI 协作项目的通用原则；AIEO 的历史返工仅作为证据案例，不限制其通用适用范围。

### 2.1 同一问题如何计数

“同一问题”按**相同根因、相同失败不变量或相同验收缺口**判断，而不是按文件名或错误文案判断。

- 第一次失败：正常复现、排查和修复，保存原始失败证据。
- 第二次失败：必须重新分析根因，书面说明第二方案与第一方案的本质区别，并补充能证明新不变量的测试。
- 第三次失败：**立即停止重复修复。** 不再通过换实现细节继续试错。
- 换会话、换 Agent、改任务名、新建 Commit、把 `FAIL` 改称 `BLOCKED`，均不会重置计数。
- 只有新方案在明确范围内取得充分证据，并经独立审查关闭该问题，才可结束本次升级；后续出现新反例应建立新的关联记录，不能删除历史。

> 历史警示：会话锁 v1–v5 连续以文件内容仲裁修补，初始化窗口和 TOCTOU 反例反复出现。今后遇到这种“同类根因跨版本重现”，应在第二次失败时考虑改变仲裁机制，而不是等到更多变体被证伪。

### 2.2 第三次失败后的强制动作

1. 汇总所有尝试：Commit、改动、测试、结果和对应证据。
2. 说明每个方案为何无效，区分已证实根因与仍未证实的假设。
3. 冻结当前状态：记录分支、HEAD、工作区、相关文件、最近可用回滚点和当前风险。
4. 至少提出一种**机制上不同**的解决思路，并说明其假设、验证方式和可能副作用；不能只提出“再试一次”。
5. 按 §6.2 生成独立 AI 审查交接报告，建议存放 `handoff/escalations/<日期>-<任务或问题>.md`。
6. 由主会话将报告、精确 Commit 和证据路径交给未参与前序修复的 AI 审查。
7. 等待独立分析；除保全证据、阻止损失扩大或按明确授权回滚外，不得继续盲目修改。

升级时可以主动建议更换模型、工具或执行方式，例如请求 GPT、Codex、Kimi 或其他合适工具独立分析。切换依据必须是当前任务需求、实际失败证据和工具适配性，而不是维护某个 AI 的面子或给模型永久贴能力标签；更换会话、Agent 或模型不会重置失败计数。

### 2.3 恢复开发的门禁

独立 AI 返回后，主会话必须记录：

- 新根因或新假设是什么；
- 为什么此前方案无法覆盖；
- 新方案改变了哪个机制或不变量；
- 哪个测试能够证伪新方案；
- 审查结论及其绑定的 Commit；
- 哪些范围仍为 `BLOCKED`。

没有这些信息，不得以“已经讨论过”为由恢复原路径循环。

### 2.4 可以提前升级的情况

以下情况不必等第三次：

- 架构性缺陷或同类竞态跨实现反复出现；
- 公共接口、数据结构、冻结契约存在错误或需要变更；
- 认证、授权、密钥、隐私、远程发布等安全风险；
- 可能重复发送、重复执行、误删数据、误改 main 或破坏历史证据；
- 真实环境无法提供关键验收证据；
- 需要用户决策，AI 无法从代码和既定规则中自行确定。

## 3. 可复用开发经验

### L-001 验收结果必须由证据计算，不能由开发者宣告

**scope:** GLOBAL（证据计算与验收原则）；AIEO（实现、字段与证据路径）  
**status:** ACTIVE  
**验证结果：** PASS（Phase 0 指定实现范围）  
**问题：** 初版 E2E 曾把 `e2e_loop_pass=true` 硬编码，工作区脏、GPT 返回 REWORK/BLOCKED 时仍可能形成成功表象。  
**有效经验：**

1. 最终成功必须是所有验收条件的计算结果；异常路径同时落盘失败状态和非零退出码。
2. 审查结果采用严格判定，REWORK、BLOCKED、证据不完整都不能穿门。
3. 工作区状态、开发测试、独立审查、两轮真实生成完成分别作为独立条件，不能互相替代。
4. 流程引擎必须提供反向测试，证明坏结果确实会失败，而不只是 happy path 能成功。

**证据：** `phase0/e2e-poc/e2e_orchestrate.mjs`；`phase0/logs/e2e-evidence.json`；反向门禁 `phase0/logs/run5-gating-demo-evidence.json`。  
**关联 Commit：** `559f627`（首轮整改落点）。

### L-002 浏览器登录失败要换受支持路径，不绕安全验证

**scope:** TOOL_SPECIFIC（Playwright/Chrome）；ENVIRONMENT_SPECIFIC（本机登录、账号与网络环境）  
**status:** ACTIVE  
**验证结果：** PASS_WITH_CONSTRAINTS  
**失败方案：** Playwright `launchPersistentContext` 直启自动化浏览器后登录，Google OAuth 拒绝，Turnstile 人工操作也未能通过。  
**根因：** 自动化直启登录链路受平台安全策略限制；项目又明确禁止隐身注入、绕过验证码或安全验证。  
**有效经验：**

1. 普通方式启动系统 Chrome，使用专用 profile 和仅绑定 `127.0.0.1` 的调试端口。
2. 用户通过邮箱人工完成首次登录；登录失效或再次出现安全验证时暂停并交人工。
3. Playwright 使用官方 `connectOverCDP` 接管已登录页面，不将登录自动化作为验收目标。
4. 专用 profile 与日常浏览器隔离；profile、Cookie 和登录态不得进 Git。
5. 该结论只证明本机 Phase 0 路径，不应扩张为所有账号、所有环境都必然如此。

**证据：** `phase0/reports/gpt-browser-validation.md`；`phase0/logs/gpt-poc-roundtrip-result.json`。  
**关联决策：** DEC-002、DEC-003、DEC-004。

### L-003 网页发送与完成判定必须证明“属于本轮”

**scope:** GLOBAL（状态分离与发送后对账原则）；TOOL_SPECIFIC（ChatGPT DOM 与 Playwright 实现）  
**status:** ACTIVE  
**验证结果：** PASS（Phase 0 已测试范围；异常时序部分由依赖注入覆盖）  
**失败链：** 只看尾帧 → 独立 `tailOk/stopOk` 闩锁 → 历史停止按钮污染 → `true→true` 时无法证明本轮生成。  
**有效经验：**

1. 发送前确认 Composer 所有权、内容回读一致，并确认当前不是仍在生成的旧轮次。
2. 发送接受必须双验：目标 user unit 前进 + 观察到本轮生成状态；命令回执或“已发送”文本不是证据。
3. 完成候选来自“可见停止按钮由有到无”的状态翻转；固定等待、正文关键词或消息计数不能单独判完成。
4. 停止按钮消失后经过 75 秒确认窗，再复查停止按钮、尾部 assistant DIL UUID、稳定读取和 Composer 空态。
5. 页面存活、消息已接受、正在生成、工具调用中、最终完成是不同状态；stream reconnect 或超时不等于未发送。
6. `SEND_STARTED` 后进程退出或状态不明，记 `UNCERTAIN` 并先对账；禁止盲目重发。已接受的消息不得为修复提取问题而重发。
7. UI 状态只使用结构化 DOM 证据；不使用会话正文中的“正在思考”等文本推断系统状态。

**证据：** `phase0/e2e-poc/completion_judge.mjs`、`e2e_orchestrate.mjs`；`phase0/logs/rework4-judge-tests.json`；R1–R4 返工报告。  
**关联 Commit：** `7c03fde`、`7c45263`、`009a2d1`。  
**边界：** `phase0/gpt-browser-poc/gpt_roundtrip.mjs` 是历史 POC，仍含早期双闩锁写法，不能不经审查直接作为新控制器复用。

### L-004 本项目跨进程互斥交给 OS，不再迭代文件内容仲裁

**scope:** GLOBAL（原子互斥原则）；TOOL_SPECIFIC（PowerShell `FileShare.None`）；ENVIRONMENT_SPECIFIC（Windows）  
**status:** ACTIVE（v1–v5 内容仲裁方案为 SUPERSEDED，禁止原样重试）

### L-007 与 ChatGPT 交接长材料：文件走 GitHub，网页只走短指针

**scope:** GLOBAL（版本化材料与短指针原则）；AIEO（1200 字节、manifest 字段及门禁）  
**status:** ACTIVE  
**验证结果：** PASS_WITH_CONSTRAINTS（公开仓库、指定 SHA、已验证材料范围）  
**有效经验：**

1. 任务书、代码、Diff、证据和长文档优先进项目 Git；网页正文只放短指令和定位指针。
2. 指针至少包含 `owner/repo`、分支、完整 40 位 Commit SHA、材料路径、任务目标和交付要求；branch 不能代替 Commit，禁止回退分支 HEAD。

2. **直连连通性随时间变化，不要下永久结论：** 2026-11-14 同日实测——上午 github.com 直连 Connection was reset，午间直连 HTTP 200；chatgpt.com 直连曾超时。**每次先绕过仓库代理直连试一次**（`git -c http.https://github.com.proxy= -c http.proxy= push`，本路径已验证成功），失败再查活代理端口，不要预设"必须走代理"或"必须直连"。
3. **排查固定路径，最多一轮：** ①读报错特征——`Failed to connect to 127.0.0.1 port NNNN` ＝ 该端口代理进程未启动，属本地服务未开而非网络问题；②`git config --show-origin --list | grep -i proxy` 确认配置层级——URL 级条目（`http.https://github.com.proxy`）优先于通用 `http.proxy`，用 `-c http.proxy=` 覆盖不了它（本次实测）；③`netstat -ano | grep <端口>` 或 `curl -I -x http://127.0.0.1:<端口> <目标>` 判断监听与可达性。
4. **连不上 ≠ 罢工：** 排查一轮仍不通，立即精确报告三要素（哪个连接、报错原文、需要用户做什么——如"启动监听 6822 的代理工具"），然后把受阻项挂起、继续做不依赖该连接的工作，条件恢复后再回来补做。禁止无限重试空转，禁止不报告就停工。
5. **受阻期间的正确产出形态：** 本地 commit 在 `.git` 里不会丢；受阻期间正常继续其他产出，维护"待推送清单"，连接恢复后一次推送，不重做任何工作。

**证据：** `phase0/environment-inventory.md` §4/§5（代理端口、Git 代理配置、直连实测）；2026-11-14 主会话 git push 复盘（6822 未监听→直连 reset→按本条路径一轮定位并报告用户）。

## 8. AI 能力边界与工具切换记录

**scope:** GLOBAL（能力边界记录与协作原则）；AIEO（已归档案例）  
**status:** ACTIVE

### 8.1 记录原则

1. 能力结论只针对**具体模型/工具版本、具体任务、具体环境和具体证据**，不得永久给某个模型贴上“擅长”或“不擅长”的标签。
2. 模型或版本没有证据时写“未记录”，不得根据会话印象补猜；工具能力、推理失误、上下文限制、权限不足和执行环境故障必须分开判断。
3. 瓶颈未获直接证据时标 `HYPOTHESIS`；不得把每次失败都笼统归因于“模型能力不行”。
4. 最终解决方式可以是改变方案、换模型、换工具、独立审查或人工介入；切换不重置返工计数，也不抹去原失败记录。
5. 新记录使用 `CAP-YYYYMMDD-NN`，关联 Task ID、Commit、原始证据和相关 `L-xxx`。

### 8.2 能力边界记录模板

```markdown
### CAP-YYYYMMDD-NN <任务中的能力边界>

- **scope：** GLOBAL / AIEO / TOOL_SPECIFIC / ENVIRONMENT_SPECIFIC（可多选并说明）
- **status：** ACTIVE / NEEDS_VALIDATION / SUPERSEDED / INVALID
- **模型/工具及版本：** <实际值；未知则写“未记录”>
- **任务类型：** <架构设计/代码实现/调试/审查/浏览器操作等>
- **Task ID、Commit 与环境：** <...>
- **失败表现：** <具体现象与影响>
- **瓶颈判断：** <上下文/工具能力/推理/执行环境/权限；标 CONFIRMED 或 HYPOTHESIS>
- **最终解决方式：** <调整方案/换模型/换工具/人工介入/独立审查>
- **可复用经验：** <后续如何避免；关联 L-xxx>
- **证据与适用边界：** <原始日志、审查回复；不得过度推广>
```

### 10.1 EXP-PLANNING-001 工程经验：项目总纲管理、阶段规划与持续可行性复评

**经验编号：** EXP-PLANNING-001
**适用范围：** 所有 AI 辅助软件工程项目
**经验类型：** 项目管理、架构治理、AI 协作管理
**建议纳入：** AI 软件工程标准——需求分析、架构设计、开发实施、项目管理相关章节

#### 一、经验背景

在 AIEO 项目开发过程中，出现了一种值得警惕的现象：

AI 执行者能够持续解决局部问题，但随着开发深入，工作内容不断扩张，单个会话承担的任务越来越多，项目整体规划与局部执行之间容易出现脱节。

可能产生以下问题：

1. 多个会话持续增加任务，缺少统一的总体方向。
2. 单个会话处理内容过多，导致上下文膨胀、重点不突出。
3. 局部方案不断完善，但没有及时验证其是否符合最终项目目标。
4. 深入实现后才发现早期技术假设不成立，造成大量返工。
5. 已经投入大量工作后，容易因为沉没成本而继续推进不合理方案。
6. 项目文档和交接内容不断增加，但整体进度、关键决策和下一步重点反而不够清晰。

因此，需要建立项目总纲管理与持续可行性复评机制。

#### 二、核心工程原则

**先确定总体方向，再验证关键可行性；先明确阶段目标，再拆分具体任务；执行过程中持续复评，发现方向性问题及时回归规划。**

具体原则：

1. 总体规划先于大规模实施。
2. 总体规划必须持续维护，而非一次性制定。
3. 每个执行任务必须能够追溯到总体规划和阶段目标。
4. 单个会话必须有明确主题、范围、输入、输出和完成标准。
5. 新发现的问题先登记、评估，不得无边界扩展当前任务。
6. 重大技术假设必须在投入大规模开发前得到验证。
7. 允许推翻已经制定但被实践证明不可行的方案。
8. 保留已经验证通过的成果，不因局部调整而无理由重复开发。
9. 项目文档应服务于工程管理，避免为了文档数量而增加维护负担。

#### 三、建立三级项目管理体系

##### 第一级：项目总体规划

负责整个项目的目标、总体架构、模块关系、实施路线和重大技术决策。

主要工作：
- 明确最终建设目标。
- 确定总体架构及模块边界。
- 制定项目阶段路线图。
- 识别关键技术风险和未验证假设。
- 评估项目整体可行性。
- 决定重大方向调整。

总体规划由项目负责人批准，AI 顾问可以提出修改建议，AI 执行者不得擅自改变已经批准的总体目标和架构边界。

##### 第二级：阶段规划与管理

负责将总体规划拆分为可执行的阶段目标。

每个阶段必须明确：
- 阶段目标。
- 工作范围。
- 前置依赖。
- 交付物。
- 验收条件。
- 风险及未解决问题。
- 进入下一阶段的条件。

阶段完成后进行复盘，确认实际成果是否符合总体规划。

##### 第三级：具体任务与独立会话

负责实际设计、编码、测试、修复和交付。

每个会话原则上只处理一个明确主题，建议控制在 1～3 项相关交付任务。

会话必须明确：
- 任务来源及关联阶段。
- 本次工作范围。
- 禁止擅自扩展的边界。
- 预期交付物。
- 验收标准。

发现范围外问题时，登记到待办或风险清单，不自动扩大当前任务。

#### 四、建立持续可行性复评机制

项目规划不是静态文件，必须根据实际实施结果持续调整。

以下情况必须触发复评：

1. 新阶段启动之前。
2. 关键技术方案首次验证之后。
3. 阶段性成果完成之后。
4. 发现核心设计与实际实现存在明显偏差时。
5. 出现重大架构问题或关键技术阻塞时。
6. 同一问题连续两至三轮无法解决时。
7. 进入下一重大阶段之前。

复评重点：

- 最初的技术假设是否仍然成立？
- 实际实现是否符合总体架构？
- 是否存在更简单、可靠的实现方式？
- 当前路线是否仍然值得继续？
- 是否需要调整模块边界或实施顺序？
- 已完成成果哪些可以保留，哪些需要修订？
- 后续工作是否应该暂停或重新规划？

复评结果可以是：
- CONTINUE：继续原计划。
- ADJUST：调整局部方案。
- REPLAN：重新制定阶段计划。
- REJECT：否定原方案，重新设计。
- BLOCKED：关键条件不足，暂停相关工作。

重大调整必须经过项目负责人批准，并记录决策依据和影响范围。

#### 五、项目总纲及规划文档管理

项目应当有一份持续维护的总体规划文件，作为所有阶段任务的统一依据。

建议根据项目规模设置以下文档：

| 文档 | 主要职责 |
|---|---|
| PROJECT-MASTER-PLAN | 项目总体目标与总体规划 |
| ARCHITECTURE-OVERVIEW | 整体架构与模块关系 |
| ROADMAP | 阶段实施路线图 |
| PHASE-STATUS | 阶段进度与当前状态 |
| FEASIBILITY-REGISTER | 技术可行性及风险登记 |
| DECISION-LOG | 重大决策与变更记录 |

以上为建议文档职责，不要求所有项目机械地创建六份文件。应优先复用现有文档，避免重复维护。

总体规划必须具有版本记录。任何重大修改都应说明修改原因、影响范围、决策人和后续行动。

#### 六、AI 协作角色与权限

项目负责人：
- 确定最终目标。
- 批准总体规划。
- 决定重大架构变更。
- 决定资源投入及阶段授权。

AI 总体规划顾问：
- 负责全局分析和路线评估。
- 组织重大技术方案讨论。
- 检查局部工作是否偏离总纲。
- 识别过度设计和无效工作风险。
- 独立评估重大调整的必要性。

AI 执行者：
- 按授权完成具体任务。
- 维护实施记录和验证证据。
- 发现问题及时上报。
- 不擅自扩大任务范围。
- 不擅自修改已批准的重大决策。

不同 AI 可以独立审查，但审查意见不等于项目变更授权。

#### 七、会话交接与工作量控制

执行会话结束时，只需要提供以下内容：

1. 完成事项。
2. 验收结论及证据位置。
3. 未解决问题。
4. 下一步建议。
5. 需要继承的关键决策和约束。

详细过程和证据保存在项目仓库，不在每次交接中重复粘贴。

发现新问题时，应先判断：
- 是否属于当前任务？
- 是否影响当前任务验收？
- 是否需要独立任务？
- 是否涉及总体规划调整？

不得因为发现相关问题就无限扩展当前会话。

#### 八、沉没成本与成果保护

当原方案被证明不可行时，不得因为已经投入开发而强行继续。

但也不得随意推翻已有成果。

必须先进行成果分类：

- 已完成且验证通过：保留。
- 已完成但尚未充分验证：补充验证。
- 已完成但需要局部修改：评估修改范围。
- 尚未实施且依赖条件不明确：暂停，先验证前置条件。
- 已证明不合理的方案：记录原因，停止继续投入。

方案调整必须尽量保留可复用成果，避免无依据的整体重做。

#### 九、最终工程要求

任何中大型 AI 软件工程项目，都应具备以下能力：

1. 能够随时明确项目最终目标。
2. 能够随时了解当前所处阶段。
3. 能够追溯每项任务的规划来源。
4. 能够识别尚未验证的关键技术假设。
5. 能够在重大风险出现时及时停止局部开发。
6. 能够通过复评调整原有路线。
7. 能够控制单个 AI 会话的工作范围。
8. 能够保留已验证成果并避免重复劳动。
9. 能够通过简洁交接维持多会话、多模型协作的连续性。

**核心结论：**

项目不能只有任务清单，还必须始终存在一份与实际进度同步的总体规划。

局部任务完成不代表项目方向正确。真正有效的 AI 软件工程，不是让 AI 不断完成更多任务，而是确保每一项任务都在为正确的项目目标创造价值。
