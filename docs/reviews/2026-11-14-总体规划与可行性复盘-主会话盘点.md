## 1. 议题逐项盘点

### 议题 1：最终目标是否清晰？——**清晰，且未漂移**

立项 01-架构 §1 的十步闭环（需求 → GPT 规划 → 架构审核 → 调度 → 智谱开发 → Git 提交 → GPT 审查 → 测试验收 → 总审计 → 用户审批）自立项以来没有变过，所有已完成工作都能挂到这条链上。问题不在目标，在节奏（见议题 5）。

### 议题 2：总体架构是否完整、合理？——**骨架合理且已实现，但有一个核心缺口**

M1 中央基座 + M2/M3/M4 执行端 + Git 证据链的架构与立项设计一致，且四模块均已实现并通过集成级审查（T-P1-902 r2 PASS）。真实缺口三个：

| 缺口 | 现状 |
|---|---|
| **中央调度引擎未工程化** | 立项架构图里最核心的 CORE（需求→批次→拆解→派单→监控→状态机推进）目前 = 人工 + 主会话工具（`gpt_dispatch.mjs` 手动派单）。它没有模块归属、没有实现条目、没有排期 |
| **测试执行 Worker 缺位** | 立项架构有 TEST 节点，M1 只做了"报告登记"，测试的真实执行与证据采集无人负责 |
| 管理后台 | `app/frontend` 仅 5 个源码文件，雏形 |

### 议题 3：已完成工作属于哪个阶段？——**名义在 Phase 1/2 交界，实际横跨计划外**

| 立项阶段 | 实况 |
|---|---|
| Phase 1 基础平台（M1） | ✅ 实现齐（15 个源码文件、45 端点、16 表）、模块审查 8 轮 PASS（T-P1-901）、集成审查 PASS（T-P1-902 r2）；只差验收清单核对（原路线 E 项） |
| Phase 2 GPT 多角色控制（M2） | ⚠️ 代码已实现（28 个源码文件），但验收走的是**浏览器模拟**；真实 chatgpt.com 只有 Phase 0 POC 级证据（单 unit、稳定 DOM、公开仓库） |
| Phase 3 ZCode 接入（M3/M4） | ⚠️ 集成套件真实跑过状态机全链（含真实 commit 采集），但 ZCode 真实领取只有 aieo-poc MCP 测试桩级 |
| Phase 4 端到端闭环 | ❌ 真实腿从未跑通（集成套件的 GPT 腿是夹具模拟，`phase1/logs/m2-gpt-controller-20261113/browser_simulation-*`） |
| **计划外** | 契约文本 C1-C8、审查协议体系、DEC-001~021、phase0 工具链、交接包制度——工作量可观，立项文档中没有对应条目 |

### 议题 4：契约/Schema/测试体系是否符合最终目标？——**方向符合，节奏超前于消费者**

消息信封、报告、C3 错误码正是十步闭环的神经系统，C3 已在 M1 错误边界真实落地（`app/platform/errors.py` 错误体结构与契约 §4.2 一致）。但按原方案 T-P1-904 要建 130+ Schema 文件/28 端点示例——**M2/M3/M4 至今没有通过 M1 REST 互通过一单真实消息**，这些 Schema 的消费者还不存在。现有 Ajv 37 例已覆盖 `contracts/v1.0/` 现有 4 个 Schema。结论：改为随消费者增量建设。

### 议题 5：有没有先做大量细节、核心前提未验证？——**有，且这是本次复盘最重要发现**

- 投入最重的单项之一：§2.6 六轮复审 + 对象身份门禁 + 14 分片聚合包 + blob 身份核对（r1-r6 跨多个完整会话）——服务对象是**一个契约小节的文本可信性**；
- M1 的 45 端点/16 表/认证/审计：实现与测试齐备，但**真实外部执行端从未通过它走过一单**（集成套件是自驱动的，GPT/ZCode 腿是测试夹具）；
- 而全项目的**命门前提——"网页自动化能否稳定支撑真实开发闭环"——至今只有 Phase 0 POC 单点证据**；
- 公平对冲：POC 验证的确是最高风险单点、契约文本是用户明令要求的、审查纪律不是浪费——**但比例失调了**。

### 议题 6：可合并/简化/暂缓/取消的工作？——主会话初步建议（待拍板）

| 动作 | 对象 |
|---|---|
| **缩编** | T-P1-904 从 130+ 文件缩到 D1 真实消费的子集（信封、错误响应、开发/测试报告、messages/tasks/reports 端点）≈15-20 个文件，其余挂矩阵 PENDING 随消费者补 |
| **简化** | 审查仪式分档：对象身份门禁保留（便宜有效）；分片聚合包仪式仅在材料超出审查环境能力时启用 |
| **合并** | phase0/tools 与 app/gpt_controller 的 git_pointer/inbound_reply 双副本，随 D1 归一 |
| **暂缓** | C2 扩展场景取证、管理后台 UI、多项目并发 |
| **冻结** | 治理文档增量——无真实故障不新增 DEC 机制 |

### 议题 7：后续阶段如何重排？——主会话建议草案（待拍板）

1. **新 P0-A**：Phase 1 验收清单核对（便宜，诚实关闭 Phase 1）
2. **新 P0-B**：**D1′ 真实端到端垂直切片**——一条真实低风险需求走完：M1 REST 建项目/批次/任务 → 真实 ChatGPT 规划会话 → 回复经 M1 REST 登记 → 状态机推进 → ZCode 经 MCP 领取 → 真实代码提交 → M4 采集 → 报告登记。**契约 Schema 子集按需即时建设**。它是核心前提的验证器，也是契约体系的第一个真实消费者
3. 之后：Phase 4 端到端闭环（多角色真实接入）→ MVP §7 清单 → Phase 5 并发
