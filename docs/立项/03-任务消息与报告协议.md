# AIEO 任务、消息与报告协议

**版本：** v0.1  
**目标：** 让 GPT、ZCode、Git Worker、测试 Worker 使用统一交接格式。

## 1. 协议原则

- 所有消息必须经过 AIEO 中央服务；
- 每条消息有唯一 `message_id`；
- 每个任务有稳定 `task_id`；
- 每个开发批次有 `batch_id`；
- 每次执行有 `execution_id`；
- 消息必须可去重、可追踪、可重试；
- Agent 输出不是最终状态，AIEO 校验后才执行状态转换；
- 任何完成报告都必须附带证据引用。

## 2. 通用消息结构

```json
{
  "schema_version": "1.0",
  "message_id": "MSG-20261111-000001",
  "message_type": "TASK_ASSIGNED",
  "created_at": "2026-11-11T20:00:00+08:00",
  "source": {
    "agent_id": "AIEO-ORCHESTRATOR",
    "agent_type": "system"
  },
  "target": {
    "agent_id": "ZCODE-01",
    "agent_type": "developer"
  },
  "project_id": "AI-IMAGE-SERVICE",
  "batch_id": "BATCH-001",
  "task_id": "T-001",
  "correlation_id": "CORR-001",
  "payload": {}
}
```

字段说明：
- `schema_version`：协议版本；
- `message_id`：全局唯一；
- `message_type`：消息类型；
- `source` / `target`：发送方和接收方；
- `project_id` / `batch_id` / `task_id`：业务关联；
- `correlation_id`：关联一次交互请求和响应；
- `payload`：具体消息内容。

## 3. 消息类型

| 消息类型 | 方向 | 说明 |
|---|---|---|
| `TASK_PLAN_REQUEST` | AIEO → GPT-01 | 请求拆解需求 |
| `TASK_PLAN_SUBMITTED` | GPT-01 → AIEO | 提交任务计划 |
| `ARCH_REVIEW_REQUEST` | AIEO → GPT-02 | 请求架构审核 |
| `ARCH_REVIEW_SUBMITTED` | GPT-02 → AIEO | 架构审核结果 |
| `TASK_ASSIGNED` | AIEO → ZCode | 派发开发任务 |
| `TASK_ACCEPTED` | ZCode → AIEO | 智谱确认领取 |
| `PROGRESS_UPDATED` | ZCode → AIEO | 开发进度 |
| `BLOCKER_REPORTED` | Agent → AIEO | 阻塞报告 |
| `DEVELOPMENT_COMPLETED` | ZCode → AIEO | 开发完成报告 |
| `CODE_REVIEW_REQUEST` | AIEO → GPT-03 | 请求代码审查 |
| `CODE_REVIEW_SUBMITTED` | GPT-03 → AIEO | 代码审查结果 |
| `TEST_ACCEPTANCE_REQUEST` | AIEO → GPT-04 | 请求测试验收 |
| `TEST_ACCEPTANCE_SUBMITTED` | GPT-04 → AIEO | 测试验收结果 |
| `AUDIT_REQUEST` | AIEO → GPT-05 | 请求批次审计 |
| `AUDIT_SUBMITTED` | GPT-05 → AIEO | 总审计结果 |
| `APPROVAL_REQUIRED` | AIEO → 用户 | 请求人工审批 |

## 5. 智谱开发任务包

每个任务包必须包含：

- Task ID、Project ID、Batch ID；
- 需求背景；
- 任务目标和非目标；
- 项目目录；
- 基线 Commit；
- 允许修改的文件范围；
- 不允许修改的目录；
- 技术约束；
- 前置依赖；
- 验收标准；
- 必须执行的测试命令；
- 适用工程规范；
- Git 分支命名；
- 报告格式；
- 阻塞上报方式。

任务包必须固定版本和内容哈希，避免开发过程中任务要求被静默修改。

## 6. 智谱开发报告示例

```json
{
  "task_id": "T-001",
  "execution_id": "EXEC-001",
  "status": "COMPLETED",
  "implementation_summary": "完成供应商接口适配器",
  "git": {
    "repository": "AI-IMAGE-SERVICE",
    "branch": "feature/T-001-provider-adapter",
    "base_commit": "BASE_SHA",
    "commit_sha": "COMMIT_SHA",
    "changed_files": [
      "src/providers/base.py",
      "src/providers/new_provider.py"
    ]
  },
  "tests": {
    "executed": true,
    "commands": ["pytest tests/providers -q"],
    "passed": 25,
    "failed": 0,
    "log_artifact_id": "ART-TEST-001"
  },
  "known_issues": [],
  "knowledge_updates_required": true,
  "self_assessment": "实现完成，等待独立审查"
}
```

AIEO 必须自行执行 Git 检查：
- 分支是否存在；
- Commit 是否存在；
- Commit 是否基于预期基线；
- Diff 是否超出文件范围；
- 工作区是否干净；
- 测试日志是否真实存在；
- 是否存在未提交修改。

开发报告中的数字不能替代系统实际采集的证据。

## 8. 测试验收报告

必须区分：
- `EXECUTED_PASS`：测试实际执行且通过；
- `EXECUTED_FAIL`：测试实际执行但失败；
- `NOT_EXECUTED`：未执行；
- `CLAIMED_ONLY`：仅开发者声称通过，无证据；
- `BLOCKED`：环境或依赖阻塞。

验收结果：
- `PASS`；
- `REWORK`；
- `BLOCKED`。

## 9. 消息可靠性

必须实现：
1. Inbox：记录收到的 message_id，重复消息不重复处理；
2. Outbox：业务状态更新与待发送消息在同一事务内登记；
3. ACK：接收方确认收到；
4. Retry：指数退避，限制最大次数；
5. Dead Letter：超过重试次数进入人工处理；
6. Timeout：超时不等于任务失败，先查询执行端和 Git 状态；
7. Correlation：请求与响应必须关联；
8. Audit：保存原始消息和处理结果。

## 10. 任务与报告的版本绑定

审查报告必须绑定：
- Task ID；
- Task Package Hash；
- Base Commit；
- Reviewed Commit；
- 工程规范版本；
- 项目知识库版本。

若代码 Commit 改变，原审查结果不能自动沿用，必须重新审查。
