# F-001 中央调度引擎最小版——立项任务书（草案 v0.1）

> **文档身份与授权链（I7）：** 本文件=立项**草案**（b-20261115-standard-kickoff S2 产出）。生效路径：会务（ChatGPT）立项评审 → **用户确认需求原文（§1）** → 用户拍板开工（DEC-010 同级红线；立项准备≠实施授权，H7）。依据：DEC-026 决议二（路线第三项）、FEASIBILITY-REGISTER F-001、b-20261115-standard-kickoff 规划（development-plan.md v0.2 阶段 C0，I1-I7 完整性框架）。

## 1. 需求原文（拟定稿，待用户确认——I1）

> "把 D1′ 已人工走通的九步真实闭环中'调度'这一环工程化：系统对**单项目、单批次、单任务**自动完成——领取任务后按状态机推进，调用 GPT 派单腿完成规划收发，登记开发执行，采集 commit 与 diff，触发测试 Worker 与审查腿，汇总状态供人工查看与介入；异常时如实登记阻塞并停等人工，不自动重试到误操作。"

- **目标：** 上述最小闭环由代码自动驱动（人工只做审批/介入），单任务全程可追溯（每步留证据指针）。
- **非目标：** 多项目/多批次/多任务并发调度；自动合并 main；自动发布；GPT-02~05 多角色全接入（逐角色属后续路线项）；DEC-017 扩展场景解锁；管理后台完善（F-005）。
- 防膨胀（规划 R1 要求）：第一期不得把中央调度平台长期建设范围整体塞入——凡本节非目标均不得顺手实现。

## 2. 背景与依据

1. **F-001 登记（OPEN）：** CORE 节点（需求→批次→拆解→派单→监控→状态机推进）无模块归属、无实现；当前=人工+主会话工具；Phase 4 多角色前必须工程化。
2. **DEC-026 决议二（用户拍板路线）：** D1′ 双分支验收 → F-003 测试 Worker（**已完成**，T-P1-907 合并 main）→ **F-001 中央调度最小版（单项目/单批次/单任务自动调度）** → GPT-02/03/04/05 逐角色 → 受控试运行（等级 B）。
3. **D1′ 先例（T-P1-905）：** 九步真实闭环全链 PASS（真实 chatgpt.com 规划收发/真实 M3 claim/真实 commit+M4 采集/报告登记），派单动作清单=`phase1/logs/t-p1-905-d1prime-20261114/RUN-RECORD.md`——本任务工程化的对象即该清单中"人工编排"部分。
4. **既有资产（消费，不重写）：** M1 平台基座（41 端点/20 表/状态机/outbox/审计，C2 契约）；M2 GPT 控制器（gpt_dispatch 工具链+fail-closed 门禁）；M3 ZCode 桥（MCP claim/submit）；M4 Git Worker（worktree/commit/diff 采集）；F-003 测试执行 Worker（`phase1/tools/test_worker.py`）。

## 3. 架构边界（I2）

- **职责：** 调度引擎=状态机推进的**驱动器**——读 M1 任务状态，按任务类型调用对应执行腿（M2 派单/M3 领取/M4 采集/test_worker 测试），把执行结果登记回 M1，推进状态；自身**不实现**执行能力（复用既有模块）。
- **归属待拍板项（立项评审决策点）：** 方案 A=M1 内调度模块（复用其 DB/状态机/outbox/审计，进程内调用）；方案 B=独立模块经 REST 调 M1（隔离清晰但多一层认证与部署）。**草案推荐方案 A**（理由：状态机与 outbox 已在 M1，D1′ 已证明 REST+DB 层稳定；最小版优先减少移动部件），**最终由立项评审+用户拍板**。
- **接口：** 上行=M1 REST/DB（任务/批次/状态/审计，C2/C5/C7 契约）；下行=M2 工具链（fail-closed 门禁沿用，C3/C4）、M3 MCP、M4 worker、test_worker（F-003 接口）；契约 v1.0.0 冻结文本不修改（H2/DEC-011）。

## 4. 状态与流程（I3——最小闭环）

单项目/单批次/单任务链：需求登记（M1 已有）→ 任务领取（M3 claim）→ 规划派单（M2 真实收发，D1′ 步骤）→ 开发执行登记 → commit/diff 采集（M4）→ 测试执行（test_worker）→ 审查派单（M2，真实腿属后续逐角色项，最小版可登记"待审查"状态停等人工确认）→ 状态推进与进度看板（M1 board）→ 全程事件审计（task_events）。每步产出证据指针（dispatch 目录/commit SHA/测试报告）落 M1 登记或任务记录。

## 5. 异常处理（I4）

| 异常 | 处理原则 |
|---|---|
| 派单发送失败/采集 fail-closed | 沿用 L-018 处置序状态机化最小版：禁重发→登记 BLOCKED→停等人工（自动补采不在最小版范围） |
| 执行腿超时 | 按 M1 outbox 既有重试→死信语义；超阈值登记 BLOCKED 停等人工 |
| 状态推进非法 | 状态机拒绝即停，登记事件，不绕过 |
| 下游 worker 不可用 | fail-closed 登记 BLOCKED，不降级伪造成功 |
| 人工介入 | 任意环节可暂停（M1 既有 cancel/审批语义）；恢复后从断点状态继续 |

## 6. 安全与审计（I5）

- 调度引擎默认**无业务凭据**（F-003 先例方案 B 边界沿用）；凭据只在 M1/C7 层。
- 所有状态推进经 M1 审计（operator/engine 标识+event_id 幂等）；重复消息/重复登记幂等（M1 既有测试语义）。
- 敏感信息不入日志不入 Git（C6/C7）；派单正文出站 ≤1200B 纪律沿用。

## 7. 验收与回滚（I6）

- **验收：** ①单任务最小闭环自动驱动全链真实执行（真实 chatgpt.com 规划腿+真实 M3/M4/测试腿，零 mock 红线沿用 DEC-028 授权文本）②状态机推进/非法转换拒绝/幂等/重启恢复负例测试③每步证据指针可追溯④异常路径（超时/不可用/BLOCKED）实测⑤独立验收（双分支惯例：开发分支+证据分支，§2.4 平台纪律）。
- **回滚：** 调度引擎为新增模块，不改 M1 既有表结构为前提（如需迁移须另列）；失败时人工编排路径保持可用（D1′ 模式不删除），可随时退回人工驱动。
