## 1. 目的与适用范围

本契约规定 Phase 1（工程管理基础平台）开发期间各参与方的角色、任务交接格式与行为红线，使执行规范不依赖任何一个会话的记忆（GPT 建议 15）。

适用对象：主会话（ZCode 编排会话）、实现子 Agent（ZCode 子 Agent）、GPT 审查会话、用户。Phase 2 及以后沿用并按需修订。

## 2. 角色定义

### 2.1 主会话（ZCode，编排者）

**职责：**
1. 冻结并守护平台级公共契约（见 `module-boundaries.md` §5），受理契约变更申请；
2. 拆解任务，按 §3 任务单模板向子 Agent 派单，每模块独立分支 + 独立工作区；
3. 收取并核验子 Agent 交付包（§4），独立执行 Git 与证据核验，不采信自述；
4. 集成：维护集成分支，执行契约兼容检查与自动化测试（GPT 建议 8）；
5. 唯一与 GPT 审查会话对接的角色：准备审查启动简报（见 `review-protocol.md` §2），转交审查结论；
6. 维护治理文件：`decision-log.md` 续记、`handoff-template.md` 实例化、审查结论归档。

**上下文纪律（GPT 建议 13）：** 主会话只保留任务状态、决策记录、接口契约、交付摘要和验收结果。子 Agent 的详细日志、完整测试输出、长代码材料一律落盘（Phase 1 证据目录：`logs/phase1/`，沿用 `phase0/logs/` 惯例），交付包只传文件路径、commit SHA 和必要摘要。

**不做：** 不代替子 Agent 写模块代码；不跳过审查直接宣布验收通过。

### 2.2 实现子 Agent（ZCode 子 Agent，四模块）

每个模块一个子 Agent，**单会话单任务**（会话锁 v6 已代码强制，见 `module-boundaries.md` §6）。

**职责：**
1. 按任务单在**自己的模块分支 + 自己的工作区**内开发，只修改"允许修改目录"内的文件；
2. 执行任务单指定的测试命令，原始日志落盘并在交付包中给出路径；
3. 按模板提交标准化交付包（§4）给主会话；
4. 接口变化即使发生在自己目录内，若涉及公共契约，必须先走变更申请，不得先改后报。

**不做：** 见 §6 铁律。

### 2.3 GPT 审查会话（审查者）

**职责：**
1. 只依据仓库实际代码与证据文件审查，**直接读 Git，不采信任何 Agent 的自述**（closeout §2.6）；
2. 按审查启动简报（`review-protocol.md` §2）逐项核验，输出三态结论 PASS / REWORK / BLOCKED（`review-protocol.md` §3）；
3. 测试结果必须绑定被审查 commit SHA；证据不足无法核实时判 BLOCKED，不误判通过。

**不做：** 不直接向子 Agent 派发修改要求——所有 REWORK 通过主会话转交；不做架构变更决策（那属于用户与主会话）。

### 2.4 用户（决策者 / 卡点处理）

**职责：**
1. 决策类卡点：合并 main 的审批、阶段进入/退出、公共契约重大变更、`BLOCKED` 中标注"需决策"的事项（04-规范 §3：`BLOCKED` 必须包含原因、责任方和解除条件）；
2. 运行卡点：ChatGPT 登录失效 / 安全验证的人工接管（Phase 0 实测：Google OAuth 与自动化浏览器不兼容）、消息 Dead Letter 的人工处理（03-协议 §9）、自动化浏览器的登录操作（邮箱方式，一次）。

## 3. 子 Agent 统一任务单模板

每次派单必须填写以下字段，作为交付核验与审查比对基准（GPT 建议 6；与 03-协议 §5 任务包要求对齐）：

```markdown
# 任务单 <TASK-ID>

- **任务 ID：** T-P1-<序号>
- **模块：** platform / gpt_controller / zcode_bridge / git_worker（四选一）
- **执行 Agent：** <子 Agent 标识>
- **输入 commit（基线）：** <完整 40 位 SHA，基于集成分支>
- **允许修改目录：** app/<module>/ 及 tests/<module>/（超出即违规）
- **禁止修改目录：** 其余全部，特别是 docs/phase1/ 治理文件、公共契约文件、
  其他模块目录、phase0/（历史证据，只读）
- **依赖模块：** <列出所依赖的模块及接口版本；无则写"无">
- **接口版本：** <公共契约版本号，见 module-boundaries.md §5；任务期间冻结>
- **验收标准：** <可判定条目，逐条可测试；来自 06-计划 §2 验收条款的分解>
- **测试命令：** <必须执行的具体命令，如 pytest tests/platform -q>
- **Git 分支命名：** feature/<TASK-ID>-<short-name> 或 fix/<TASK-ID>-<short-name>（04-规范 §6）
- **交付期限：** <明确时间点>
- **报告格式：** 标准化交付包（本契约 §4）
- **阻塞上报方式：** BLOCKER_REPORTED 消息，含原因/责任方/解除条件（03-协议 §3）
```

任务单内容哈希固定（04-规范 §7：`task_package_hash`），派发后不得静默修改；需要变更时生成新版本任务单并记入 `decision-log.md`。

## 4. 标准化交付包模板

子 Agent 完成任务后向主会话提交，主会话凭此独立核验（GPT 建议 9；与 03-协议 §6 开发报告对齐）：

```markdown
# 交付包 <TASK-ID>

- **分支名：** <feature/T-P1-xxx-yyy>
- **commit SHA：** <完整 40 位 SHA>
- **父 commit SHA：** <应等于任务单的输入 commit，供审查比对>
- **变更文件清单：** <逐文件列出；不得超出任务单允许修改目录>
- **接口变更说明：** <若触碰公共契约必须说明并附变更申请编号；无则写"无">
- **测试原始日志路径：** <logs/phase1/ 下的具体文件，日志内注明被测 commit SHA>
- **测试环境：** <OS/Node/Python/Git 版本；Phase 0 实测基线见 handoff §7>
- **已知问题：** <如实列出；无则写"无">
- **回滚方式：** <如"删除分支 <分支名> 即可，集成分支未受影响">
```

主会话核验清单（缺一不可，依据 03-协议 §6）：
1. 分支存在且 commit 存在；
2. commit 基于预期基线（父 commit SHA 一致）；
3. Diff 不超出允许修改目录；
4. 工作区干净（无未提交修改）；
5. 测试日志真实存在，且日志内的 commit SHA 与交付包一致。

## 5. 通信与上下文纪律

1. **子 Agent 不直接对接 GPT 审查会话**（closeout §2.6 ★）：子 Agent → 标准化交付包 → 主会话 → 审查启动简报（含 commit SHA + 证据路径）→ 审查会话；
2. **审查只认 commit 与证据**：审查会话直接读取 Git 实际代码和原始证据文件，Agent 的口头/文字结论一律不作为验证结果（GPT 建议 9）；
3. **长输出一律落盘**：超过一屏的命令输出、测试日志、审查材料写入 `logs/phase1/`（延续 `phase0/logs/` 惯例），对话中只出现路径与摘要（closeout §3.3）；
4. **消息协议**：Phase 1 各 Agent 间消息结构遵循 03-协议 §2（schema_version / message_id / correlation_id 等），Inbox 去重由平台基座实现。

## 6. 铁律（红线）

违反任一条，交付包直接退回，情节记入 `decision-log.md` 并上报用户：

1. **子 Agent 不得私改公共契约。** API 协议、数据模型、错误码、日志格式、分支策略、配置命名以 `module-boundaries.md` 冻结清单为准，变更必须走统一变更申请（GPT 建议 7、风险 9）；
2. **子 Agent 不得直接合并 main，不得直接推送 main**（04-规范 §6 规则 3、9；MVP 明确不纳入"自动合并主分支"，06-计划 §8）；
3. **子 Agent 不得直接对接审查会话**（closeout §2.6 ★）；
4. **交付以 commit + 可复现证据为准，不采信自述**（closeout §2.6 ★；03-协议 §1"任何完成报告都必须附带证据引用"）；
5. **每模块独立分支 + 独立工作区，不允许多个 Agent 同时写同一工作目录**（04-规范 §6；GPT 建议 8）。公共文件（治理文件、契约文件、集成分支）由主会话修改；
6. **Agent 只能提交事件/报告，不能自行把任务置为 ACCEPTED**——状态机由平台基座唯一持有（04-规范 §3）；
7. **网页自动化失败不得伪装为任务完成**；无法执行必须报 BLOCKED 并说明原因（03-协议 §8 `CLAIMED_ONLY`/`BLOCKED` 语义）；
8. **被修改的 commit 必须重新审查，旧审查结论失效**（03-协议 §10、04-规范 §6 规则 8）。

## 7. 独立集成验收阶段（GPT 建议 14）

四模块开发完成后，不直接宣布 Phase 1 完成，必须经过独立集成阶段：

1. 主会话**冻结候选集成分支**；
2. 运行跨模块契约测试 + 完整 E2E（对应 06-计划 §2 验收七条：创建项目/批次、父子任务与依赖、状态机符合、消息不重复处理、重启状态不丢失、进度只计 ACCEPTED、操作有审计）；
3. 修复必须产生新 commit 并重跑受影响测试；
4. 最终由**独立审查会话**针对最终候选 commit 验收（按 `review-protocol.md`）；
5. 全程结论绑定 commit SHA，存档 `phase0/logs/dispatch-*/`（Phase 1 为新 dispatch 目录）。

## 8. 违规处理

| 违规 | 处理 |
|---|---|
| 交付包与 Git 实际状态不符 | 交付退回，按 REWORK 记录 |
| 越界修改目录 | Diff 核验发现即退回；触碰治理文件/公共契约的，恢复原状并记 decision-log |
| 私自对接审查会话 | 审查结论作废，重新走简报流程 |
| 自述通过但证据缺失 | 主会话判 BLOCKED，不进入验收 |
